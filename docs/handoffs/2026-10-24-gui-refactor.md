# 下一聊天工作方式交接（GUI 重构任务）

日期：2026-10-24。

本文件只交接用户约定的工作方式，不提供 GUI 重构方案，也不规定页面布局、技术选型、代码拆分或验收用例。具体如何重构，由下一聊天根据用户要求和项目实际情况研究决定。

## 主 Agent 与子 Agent 分工

- **主 Agent**负责理解目标、阅读资料、设计思考、规划、任务分配、接口/架构审查和最终整合，持续跟进至完成，不独自承担全部编码。
- **关键代码编写**交给 **6.1 Sol，高思考**的子 Agent。
- **简单、机械、低风险、结果明确的固定检查**交给 **6 Luna，高思考**的子 Agent，例如按确定命令执行回归、strict 和文档链接核对。
- **权限设计、故障归因、架构判断**由主 Agent或 **6.1 Sol，高思考**处理；Luna 遇到异常应保留证据并交回，不自行放宽断言、跳过失败或修改验收标准。
- 用户曾明确要求方案思考由主 Agent 完成，不分发给子 Agent。因此规划和设计思考应由主 Agent 主导完成；编码和固定执行仍按上述分工安排。若下一聊天有新的明确指令，以新指令为准。

不要用其他模型或低思考强度替代用户指定配置。分派时明确模型与思考强度，不仅在任务描述中口头约定。

## 如何分派与整合

主 Agent 先阅读需要的项目文档，尤其是 [docs/guides 下的开发约定](../guides/development.md)，再定义可交付的任务。当前文档入口为[文档导航](../README.md)、[开发者指南](../developer-guide/README.md)和[用户指南](../user-guide/README.md)。

每个子任务应写清：

1. 目标、范围、允许修改的文件及不能触碰的边界。
2. 依赖的接口与需要遵循的文档。
3. 当前属于开发阶段还是测试阶段，哪些动作尚未授权。
4. 完成标准，以及必须返回的修改清单、接口影响、实际验证结果和未决问题。

可并行处理边界独立的任务；避免多个 Agent 同时修改相同文件或未经协调地改变共享接口。发生交叉修改时，由主 Agent 统一协调和整合。

主 Agent 必须审查实际改动与接口影响，不能只转述子 Agent 的完成报告。遇到失败由主 Agent 判断下一步，必要时交 Sol 定位和修补，再交固定执行 Agent 复核。

## 开发与测试分阶段

用户多次要求将开发与测试分开，按下一聊天的具体授权推进：

1. **规划**：明确本轮目标并将计划存档。
2. **开发**：完成约定范围的实现和整合，更新必要文档；如果用户要求“先不测试”，不得自行开始测试。
3. **开发交付**：说明已完成内容、剩余问题，提交最小测试清单；不要把“开发完成”写成“测试通过”。
4. **测试**：用户要求开始测试后，执行约定清单，记录首败、原因、修补和复测结果。
5. **收尾**：依据结果选择继续改进或完成；暂时难以解决的问题记录后按用户决定搁置。

测试应覆盖实际行为与边界，不通过硬编码、放宽断言或跳过失败来制造通过结果。测试记录应区分通过、失败、跳过、未执行和环境限制，并保留真实退出结果；没有实际验证的内容不能宣称已通过。

尽量使用能证明目标能力的最小清单，避免无变化反复运行昂贵批次。新测试的内容由下一聊天结合实际改动设计，本文件不预设 GUI 测试方案。

## 方案调整、问题记录与沟通

用户允许在实现中发现原方案不合适时主动调整，选择更好的实现，但必须实现总体目标，不能用硬编码敷衍。主 Agent 应解释重要调整的原因、影响，并同步文档。

实在难以解决的问题可以记录后暂缓。记录不能只写抽象风险，应结合已有证据举例说明“什么情况下会出现什么问题”，区分已观察到的现象与尚未证实的推断。已由用户搁置的工作，不要在新任务中自行恢复。

工作中持续提供简短进展，说明完成情况、阻塞点和下一步；遇到中断先核对现状和已完成结果，再继续，避免重复开发或遗漏未整合工作。已有授权和约定继续有效，不要反复询问相同问题。
