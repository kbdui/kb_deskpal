# 记忆整理频繁重试的排查

## 已确认的原因

真实模型复现表明，主要问题发生在模型已成功返回之后：模型认为“采用已有记忆”只需要指出记忆编号、决定 adopt 和理由；宿主却要求再次给齐内容、类别和原始依据。当前宿主只为 retain（保留）和 archive（归档）继承已有字段，adopt（采用）仍需要完整输出。因此，一个没有修改正文、只是确认已有理解的决定，也会因缺失 content、destination、claim_type、quote、sources 五个字段被拒绝。

提示词虽然说明“其他变更须给 memories 同类字段”，但先列出 reviews 的编号、决定、理由，又将采用、修改、合并放在同一组，容易让模型把“采用”理解为单纯变更状态。输入中的已有理解同时包含 status、original_source_key 等输入专用信息，原样复制到输出也会触发严格字段校验；这是另一条可能的失败路径，本次真实复现没有出现多余字段，不能把它当作历史错误的已确认原因。

第二次请求只告诉模型错误码 fields_invalid 和位置 reviews[0]，没有给出字段差异或上次输出。模型必须重新生成整份提议，却不知道具体少了哪几个字段。复现时，两种场景的第二次请求都重复遗漏同样五个字段。这里“接口成功”不等于“记忆保存成功”，不能将网络正常或调用账本的 finished 当成学习成功。

## 为什么影响次数、等待和开销

每份提议中任意条目的字段、证据或提交约束不通过，都可能使整个整理作业再次调用模型，最多三次。定期后台复查也会选取尚未完成覆盖的记忆；同一修订还有单独的尝试限制，并非无限重试，但仍可能跨多个后台批次重复遇到同类协议问题。后台复查与聊天工作共用 Dispatcher，已开始的复查可能让新聊天排队；同步聊天整理又必须结束后才能发布最终回复。

此前只读检查的范围是北京时间 2026-11-10 00:00 至 2026-11-11 10:29：19 项外层任务、53 次模型调用，其中记忆评估 33 次；15 次 reviews[0] 字段校验失败，2 次提交提议校验失败。3 个后台学习作业三次耗尽后失败，未保存学习记录，外层任务则保存“内部工作已结束”的完成状态及警告。历史日志没有模型原始输出，无法追溯那 15 次各自具体遗漏或多出什么，也不能将它们全部归因于本次复现的五个字段。

## 真实模型复现

使用当前配置的 deepseek-flash，只发送合成事实与合成习惯缓冲，两组各执行首次请求及一次现有纠错请求，共 4 次。全部成功获得接口响应，又全部因 adopt 缺失上述五个字段被宿主拒绝；没有网络错误、JSON 解析失败或输出截断。测试只走输出评估，不向真实记忆数据库提交。

累计输入 5,272 tokens、输出 9,024 tokens，其中接口报告 reasoning_tokens 为 8,569；模型请求耗时合计约 61.4 秒。这说明重复生成还会重新付出推理开销，不只是重传几个字段。此计量不代表账单价格，也不是对所有实际聊天的统计。脱敏计量记录在 `build/memory-feedback-live-20261111.json`，未保存完整提示词、正文、密钥或模型原始回复。

## 本次补充的诊断

沿用现有逐次调用账本的 JSON metadata，不增加数据库表或执行迁移。原有请求大小、token、耗时、接口错误码继续保留，新增：

| 字段 | 用途 |
|---|---|
| processing_stage | 区分模型调用、JSON 解析、字段补全、协议校验、业务提交。 |
| processing_rule | 区分字段集合、类型、空文本、字节限制，以及习惯缓冲、采用投递、合并目标、跟进时间等提交约束。 |
| processing_missing_fields / processing_extra_fields | 记录技术默认值补全之后仍缺失或多余的字段，另有精确数量。 |
| processing_expected_type / processing_actual_type | 记录预期与实际 JSON 类型，不记录字段值。 |
| processing_decision | 记录采用、保留、修改等固定决定类别，便于确认失败是否集中在某种操作。 |
| processing_actual_bytes / processing_limit_bytes | 文本校验失败时区分长度限制和其他问题。 |
| processing_json_line / processing_json_column | JSON 解析失败的位置，不保存附近正文。 |
| learning_kind / learning_attempt / learning_attempt_limit | 区分本轮整理或后台复查、当前次数与上限。 |
| learning_correction / learning_catalog_count / learning_understanding_count | 记录是否带纠错提示、本次资料和已有理解的数量。 |
| learning_outcome | 区分已保存、检索历史、提议被拒、连接失败、来源失效、提交失败和保存后的投递待恢复。 |

字段名和类别均经过白名单过滤，未知字段名统一标为 unknown；具体数量仍保留，不写任意异常正文或字段值。新增信息自应用重启后的新请求生效，不回填旧记录。部分原本统一归为 proposal_invalid 的结构错误现在有更具体的诊断分类，接受/拒绝边界不变；没有调整采用规则、重试上限或模型纠错提示。

## 建议的后续修复

“采用已有理解且未修改正文”可以与“保留/归档”一样继承已保存的内容和来源，宿主仍核对真实编号、修订及原始依据；真正修改或合并时才要求修改内容和相应依据。这样不需要模型重述五个没有变化的字段，也不需要放松证据检查。

同时，应将本次新增的字段差异和具体约束加入下一次模型纠错提示，避免只说“第一条无效”。未知字段不宜无条件丢弃；由宿主明确区分可继承字段、输入专用字段与模型必须明确决定的业务内容。再按新增日志观察是否存在来源、习惯投递或时间约束的独立失败。

## 同日修复：采用原内容、明确纠错并验证实际保存

在用户要求修复后落实上述建议。纯 adopt 允许只给真实编号、采用决定和新理由，宿主从已加载的同一条记忆继承正文、类别、性质、人物、原文引用、来源和时间；模型明确给出的值不会被静默覆盖。更换正文、人物、类别、性质或有效时期，以及 temporal=true、update、merge，仍要求完整修改及实际依据。真实编号、修订、原始来源和习惯投递的检查继续执行，不能用“继承”创造新来源或改换人物。

提示词明确区分纯采用和修改，说明 status、original_source_key 只属于输入资料；采用 habit 缓冲时须同时输出 habits，并将 buffer_id 指向同一条缓冲，使采用结果确实进入人格。下一次纠错请求现在接收经过脱敏的字段差异、类型和字节限制；若失败在业务提交阶段，还附对应的中文规则，例如“采用习惯缓冲时同步输出习惯”，不再只有“第一条无效”。网络重试会清除旧的提议纠错信息，历史补查仍是独立步骤，最多三次的预算不变。

先以离线真实临时库验证事实采用与习惯投递，首轮 24 项通过。随后使用同一真实模型 deepseek-flash 和三个独立合成档案走实际后台：事实复查一次调用后写入 accepted；习惯复查一次调用后缓冲归档且人格新增一条习惯。第三例人为在首次模型输出中加入不支持的 status 字段，宿主准确拒绝，模型收到明确纠错后第二次通过并保存；这次失败属于测试注入，不是自然出现的故障。三组共四次真实请求均有成功接口响应，最终三个学习作业均 completed 且有保存记录。真实模型记录及纯合成数据库位于 `build/memory-retry-fix-live-20261111-a1/`，没有读写真实角色档案。

边界复核时又收紧纯采用条件：不能通过保留正文、单独改变 valid_from/valid_to 来绕过完整修改要求；相关测试覆盖事实性质、人物、类别、正文、时间变化，字段错误后的恢复和日志持久化。此次没有改变后台复查的时间间隔、同步学习顺序、免打扰机制，未重放已有失败作业或重置真实档案的尝试次数；重启后新请求和后续复查使用修复后的规则。自动测试和少量真实请求证明这些场景可用，不表示任何复杂提议都不会再需要纠错。
