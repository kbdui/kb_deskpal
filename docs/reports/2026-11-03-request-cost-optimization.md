# 2026-11-03 模型请求开销与诊断优化

本次落实用户选择的六项工作：保存逐次诊断、按原因重试、简化输出协议、减少每轮旧记忆复核、合并上下文理解与首次规划、压缩提示词和输入。保留自动学习、发布前同步整理和独立的最终润色，没有引入“由模型决定本轮是否学习”的额外门控，也没有修改模型思考模式或真实连接配置。

## 1. 一次普通聊天现在怎样运行

旧链路是“独立理解交流需求 → 检索 → 首次规划 → 同步学习 → 最终表达”。普通成功聊天需要四次模型调用，同一批角色和前文会在理解与规划两次发送。

新版先读取适用角色、近期对话、有效摘要和原句检索结果，再交给**同一次首次规划**。模型既判断怎样聊天，也提出答复或行动；交流需求可随这次决定一并返回。普通成功聊天因此为三次调用：首次规划、同步学习、最终表达。这里的 25% 是这一种路径的调用次数降幅，不是费用降幅。

如果“那件事”等指代需要补查，首次决定可提供带来源的查询线索。程序先补查，再让模型依据新资料判断行动；第一次提出的工具不会提前执行。多轮工具、澄清、必要补查和失败修正仍按真实需要增加调用，不把所有任务硬压成三次。主动行为原有权限和来源边界保留，不凭主动机会获得用户授权。

交流要求通过 `context.entries` 返回，可选检索通过 `context.retrieval` 返回；原生工具决策可附带 `turn_context` 元数据。它不注册为实际工具，不产生执行步骤或权限。范围、期限、真实来源和修订仍由原服务验证。可选理解无效时保留原设置，给出提示，沿有效原资料再判断；不会让无效线索中的工具直接执行。来源被撤销或角色修订冲突仍阻止晚到提交。首次采用标记随任务保存，续办不重新运行独立理解。

## 2. 重试从“再试一次”改为“看哪里失败”

| 原因 | 当前处理 |
|---|---|
| 超时、网络故障、HTTP 408／429／5xx | 在原三次总额度内重试；第一次等待 250 毫秒，第二次 500 毫秒；不把连接错误说成模型理解错误。 |
| JSON、字段、时区、引用或提议校验失败 | 再次生成时加入固定错误码和字段路径，例如 `time_invalid / memories[0].review_after`，不回放整份错误正文。 |
| 永久 HTTP 错误、输出上限截断等非临时提供方错误 | 停止重复发送相同学习请求，保留失败回执，继续按实际结果形成回复。 |
| 修订冲突、来源失效、取消或关闭 | 不让模型靠重新生成覆盖新数据；来源或任务失效则停止本轮提交。 |
| 存储／提交异常 | 不通过重复调用模型修磁盘问题；已经提交的工作不倒退为未完成，不重放工具。 |

学习发起和完成仍分别记录，单项工作最多三次尝试。等待期间也检查取消和来源，不跨模型等待持有数据库锁。一次网络失败后恢复时不附加“修正 JSON”提示；只有确实未通过提议校验时才要求修正。

## 3. 输出协议和旧记忆复核

反馈模型可以省略没有变化的组，`{}` 正式表示没有学习变化。程序补齐空数组、空值和技术默认字段。保留／归档已有理解时，可省略没有修改的正文、归属和原文引用；这些值从本轮冻结的原记录补齐。新增、采用、改变或合并的理解仍必须给出实际依据，不能凭默认值创造事实。时间仍要求带时区的完整日期时间，原话引用、修订、用途与授权检查没有取消。

前台每轮从最多十六条旧理解缩减为**最多五条相关理解**，候选与已接受内容都可参与。优先资料来自本轮召回、当前任务或近期实际对话关联，也保留文本相关检索作为补充；这只是选择输入，不判断事实真假。完全无关的旧记忆不再每轮附送。独立后台整理保留原有冻结批次和十六条上限，没有撤掉公平轮转。未被前台选中的旧理解，可能到明确提及、有效召回或后续后台复查时才修改；不能宣称每轮已经检查全部记忆。

## 4. 提示词和输入具体压缩了什么

`planner/llm_planner.py` 将规划指令收敛为角色视角、自然交流、前文与事实区分、实际工具结果、多轮行动和主动边界，再附首次决定专用的交流／检索说明。`memory/feedback.py` 将字段定义、来源、缓冲、情绪、关注和摘要规则合成较短协议。`response/composer.py` 缩短重复说明，保留自然承接、不强求建议和追问、提议不等于事实、失败查询不证明不存在、待确认草案标记、真实学习回执和澄清问题等约束。

新增模型视图层统一处理冗余包装：角色记录的长标识改成本轮短编号，由程序映射回真实记录；宿主修订、来源索引、用途和删除追踪仍完整留存。历史保留原话、用户／助手身份、提议性质及必要稿件版本，执行结果保留成功／失败／未知及原内容。有效摘要保留内容与非权威标注。学习输入中，同一段历史只在来源目录放一次，其他位置引用目录编号；不再重复整份历史和当前草稿。记忆证据使用紧凑对象，避免把 JSON 再包成转义字符串；请求传输也使用紧凑 JSON。

没有用关键词截断用户消息、工具实际结果、否定含义或追加要求。工具参数定义仍完整提供，角色卡内容、情绪含义、相关记忆及安全约束没有为了字节数直接删掉。

## 5. 后续怎样定位开销

新增服务端用量 DTO 和任务调用诊断，逐次保存开始／完成时间、耗时、逻辑输入字节、回复正文字节、服务端报告的输入／输出／缓存／推理 token、响应标识及固定错误分类；反馈校验另外标记字段路径和处理结果。逻辑字节不等于 HTTP 报文大小，回复正文字节不包含原生工具调用参数。服务端未提供用量时保持未知，不用字节估算 token，也不伪造历史失败正文。

诊断位于工作流库新增的 `model_call_diagnostic`，关联既有调用账本；一次失败后成功，会保留两次独立记录。`ApplicationService.diagnostics()` 返回最近二十次，底层支持读取最近一百次。记录不含请求／回复正文、认证头、异常原文或模型私有思考。诊断写入失败不会触发模型重发；已清理记录的晚到更新不会将其重建。进程中断的未完成调用仍算已占用额度，重启只标记结果未知，不自动补发。

工作流库正式升级为 schema 6，其他三库版本不变；沿原机制先保留升级前单库快照，再在事务中新增诊断表和索引。归档检查和完整备份识别新版本，旧归档在正式打开时升级。本次开发没有启动真实用户档案，实际迁移在更新后重新打开应用时发生。
