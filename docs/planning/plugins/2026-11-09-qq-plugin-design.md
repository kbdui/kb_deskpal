# QQ 插件开发设计与已确认范围

日期：2026-11-09；最近更新：2026-11-15。状态：完整文字私聊/群聊及其人物认知、长期约定、主体记忆读取和角色经历回流已接入代码，并补充群聊节流；核心契约及节流已做合成自动化验证。真实模型、NapCat 收发、数据库实档升级和窗口交互尚未联调验收。本文第一节为最新范围。

2026-11-14 补充：QQ 表达支持一次生成、多条依次发送，以消息组和逐条回执管理投递；不逐句调用模型。规划与表达提示词明确虚拟角色的定位，不能从人设或想象编造已经发生的线下生活。具体设计见第八节。

2026-11-14 当前决定：模型在最后一次规划中独立给出 action 与 organize_memory；quiet 可以整理，answer 也可以暂缓。取消同日较早的“quiet 默认跳过、回复必整理、累计八份触发”方案，不增加一次模型判断。QQ 选择整理时处理插件内社交记忆，并可将重要经历经持久发件箱投递给主体。完整约定见 [是否回复与是否整理记忆方案](../companion-model/2026-11-12-quiet-and-memory-consolidation.md)。

本次明确替代此前“先改造主体为通用多人系统，再接入 QQ”的路线：主体保持角色与本机用户一对一；QQ 插件管理自己的社交数据、处理流程与记忆。角色身份与人格共用，联系人认知、群聊状态及人物专属约定隔离在插件中。此前的[通用多人方案](../companion-model/2026-11-11-multi-person-integration-design.md)降为历史备选，其中人物与归属设计已下沉插件。28/29 日原始讨论不改写，后续明确决定优先。

## 一、2026-11-14 纠正后的完整聊天范围

用户明确“首版只做多人/单人聊天”的原意是排除改账号资料、发动态等聊天之外的功能，不是删除人物认知、长期记忆或主体经历接收。此前把后者列为未来功能是实现范围理解错误，现予纠正。当前范围包括文字私聊/群聊、人物与社交账号分离、跨私聊/群聊的人物认知、相处约定、转述归属、旧消息按需回看、当前会话原生 @ 与引用回复、分条发送和真实回执、角色人格/情绪/主体私人记忆读取，以及重要经历以角色视角回流主体。

不实现改账号信息、发动态、好友/群拓展和复杂群管理。当前仍以文字为范围，非文字仅作占位，不声称已经理解图片、文件或语音。不增加主体 PersonRegistry，不把 QQ 群放进主体会话列表。已知人物的认知和约定属于聊天基础能力，已在插件内建模，不再整体推迟。

来信先去重入队，经统一 Dispatcher / AgentCore 判断；群聊默认被 @ 或引用回复角色时触发，也可明确选择全部文字消息。另支持模型登记的内部复查及现有会话后续聊天机会；主动聊天须本机单独预授权，不随机开聊或添加联系人。所有模型调用仍在唯一 worker，周期检查只投递工作。模型可以 quiet，不必发送；qq_send 内一次表达生成 1–6 条并按序发送，逐条核对实际账号、暂停和授权，不在桌面聊天重复回复。organize_memory 独立控制插件社交整理，不把 QQ 发言套入主体默认一对一学习。

2026-11-15 来信节流：普通群消息首条合并 10 秒，后续任务默认至少间隔 60 秒，可选 30/60/180 秒；@ 与引用回复合并 2 秒、突破普通冷却，同群直接呼叫之间默认至少 10 秒，此限制可在 QQ 设置关闭。实际首次规划消费冷却，quiet 同样计入，重启持久保留。群聊优先最新有界消息批次，旧积压只撤下独立唤醒资格，原文、未看与未整理状态不伪造。没有新消息不因间隔唤起模型；内部复查/已登记跟进另走原机制。待执行插件任务让本机请求优先，不抢占运行中的任务。无需新增模型判断是否触发。

同一角色的人格、情绪和主体私人记忆可供 QQ 理解、规划和表达使用。主体记忆按相关性召回，并可通过受限只读工具补查，遵守既有用途/失效校验；不逐轮拼入全部桌面聊天。本机用户理解保留 local:user 归属，不能冒充 QQ 联系人。是否适合向当前对象透露资料，由模型结合真实来源和场合判断。QQ 人物以账号区分，同名不合并；转述对象没有账号时保留未确认名称，不猜账号。

QQ 工具包括当前会话发送、原文回看、QQ 认知检索、主体记忆只读检索、当前会话跟进登记/取消及时间。内部复查禁止发送；未来主动聊天须现行预授权，执行中撤销同样有效。本机文件、终端、截图和主体角色直接修改仍不开放，越界直接未执行，不转桌面审批。配置和暂停仅由本机页面操作，QQ 消息正文不能改授权。

实现与使用细节见 [QQ 文字聊天使用说明](../../user-guide/qq-chat.md)，静态审查与未验证范围见[实施日志](../../reports/implementation-log.md)。

## 二、协议端与安装

沿用已选 NapCatQQ / OneBot 11。NapCat 负责登录和协议收发，插件负责社交业务。开发阶段由用户在项目之外自行安装 NapCat 并登录；DeskPal 配置连接参数，测试连接后读取并核对账号编号、昵称和在线状态。填写账号名称本身不是登录；首次登录或状态失效时按协议端要求扫码或验证。具体协议行为以开发时固定的兼容版本验证。

Git 只保存插件代码、配置模板、兼容版本和安装说明，不提交 NapCat、QQ 客户端、登录状态、二维码、Token、实际配置及运行日志。未来打包可以考虑在用户数据目录管理可选协议端，安装、升级和回退不作为首版前置。项目为个人爱好、开源、非商用；这不替代第三方组件的许可，未来捆绑或自动下载仍需核对当时许可。

## 三、坚持插件四部分边界

| 部分 | QQ 插件负责 | 宿主提供或保证 |
|---|---|---|
| 主动行为与事件源 | 连接事件、私聊/群聊消息订阅、社交跟进和联系人主动联系机会 | 受管注册、合并去重、串行调度、预算和档案生命周期 |
| 插件能力 | 读消息、理解交流、范围内社交动作、组织回复、润色发送、社交记忆整理 | 公共模型连接与逐次诊断、受限工具执行、实际授权校验 |
| 额外数据库 | 人物与账号、原始消息、社交记忆、相处约定、发送回执及学习/投递作业 | 插件存储命名空间、迁移与备份恢复、关闭和删除生命周期 |
| 图形界面 | 连接配置、账号状态、授权入口、交流/执行记录、暂停 QQ | 插件页面容器和受保护设置操作接口 |

插件拥有社交数据与局部上下文的组织、工具和整理能力，不把来信提交为主体用户发言。理解、规划和多步工具执行可复用 Dispatcher / AgentCore；是否整理由最终 organize_memory 决定，不强制另写完整 QQ Agent。共享模型连接、诊断、预算和串行队列；真实外部来源、局部资料和权限仍需接入，不能将 QQ 联系人冒充 local:user 或主动用户任务。

新链路为：QQ 事件或主动机会 → 插件持久保存与去重、登记可信来源 → 复用执行链结合共享角色资料和插件局部记忆理解/行动 → 插件内润色发送并登记结果 → 模型选择 quiet，并独立判断 organize_memory → 需要时整理插件资料，否则暂缓 → 保存实际状态，不在主体聊天重复回复。重要角色经历经受控入口选择性分享主体。

复用 AgentCore 会读取同一角色的相关人格/记忆，但不直接使用主体默认一对一 FeedbackLearning 整理 QQ 原文。QQ 的 organize_memory=true 由可信入口装配的插件整理实现处理局部资料，并可建议分享重要经历；false 仅保存实际交流及结果。不通过正文指定 memory_backend。发送留在插件，不自动转述日常聊天；主体经历接收与学习是独立的持久链路。

## 四、唯一角色与社交数据隔离

角色卡、身份、已学习人格及当前情绪由主体提供只读上下文；QQ 可以读取主体私人记忆，并按相关性补查。插件不复制可独立修改的角色人格，也不直接改 companion 数据库。主体中的本机用户理解与相处要求仍保留所属对象；模型结合当前 QQ 人物与场景决定如何应用及是否透露，而不是程序一律禁止读取或一律推广给所有人。

QQ 中对 A 的认识、对 B 的印象、群内临时交流方式、人物专属相处约定、对一次社交的局部反应，均属于插件数据及上下文，不覆盖主体对本机用户的要求。每位联系人不是一个新角色，不复制完整人格。QQ 经历若确实促成角色整体成长，通过受控经历入口和主体后续学习形成变化；“对小明少追问”不能直接成为全局习惯。插件不直接写主体当前情绪；有价值的实际社交经历可以成为主体后续理解和情绪更新的依据。

## 五、插件社交数据库与多人建模

实际使用当前角色档案内的 `plugin_qq.sqlite3`，当前结构版本为 3，兼容从先前版本 1/2 事务升级，保留旧消息和发送回执；旧未认领群积压不自动批量补答。主体四库不增加人物表；插件库纳入备份、恢复、切换及删除。以下为概念对象与实际表的对应，不建设额外人物画像模型或完整知识图谱。

| 插件内对象/实际表 | 主要内容与约束 |
|---|---|
| qq_person / qq_identity | 人物编号与平台账号分离，账号保存 platform、namespace、external_id。以实际 QQ 号建立关联，跨私聊/群聊一致；不按昵称或模型猜测合并不同账号。多个账号归一的人工确认入口不属于首版。 |
| qq_message | 账号和会话作用域下的实际发言者、原正文、已确认发送正文、时间、原生 @ 和引用对象；群不是人物，群内点名不改变可见范围。已知参与者从真实消息取得，不假装拉取完整群成员列表。 |
| qq_social_memory / qq_social_link | 事实、印象、经历和约定的正文、状态、修订、理由、不确定性、复查时间及实际消息依据；关联来源人、内容对象、观点持有人及参与者。未知对象保留名称和未确认人物关联。 |
| qq_social_memory.kind=agreement | 与人物或当前会话的长期约定；冲突由模型结合场合处理，不增加好感度或数字优先级，不直接改主体人格。 |
| qq_work / qq_send_batch / qq_send_command | 工作、实际规划输入、真实请求人、触发方式、复查对象、目标会话及逐条发送回执。固定消息组正文和引用/@参数；部分成功与未知分别保存。 |
| qq_learning / qq_message.organized / qq_summary | 冻结整理输入及修订、有限重试、实际正文覆盖和会话摘要；未纳入预算或失败的消息不假标完成，旧未整理消息可在后续批次发现。 |
| qq_experience_outbox | 一项 QQ 整理的固定角色经历及来源事件、待投递状态、实际接收回执、尝试次数；同一投递不换正文、不因主体遗忘重新投递。 |
| qq_followup / qq_review_attempt | 模型登记的内部复查或预授权主动聊天，及待确认认知到期检查。内部复查没有发送能力；同修订无进展会延长操作级重试间隔，不据年龄删除记忆。 |
| qq_group_gate / qq_message.received_at、direct_call / qq_work.started_at、direct_call | 每群普通/直接呼叫的实际启动时间、宿主收到消息时间和直接呼叫标记。仅控制唤醒时机，不能代替规划输入覆盖或记忆整理完成状态。 |

人物认知摘要可按需从有效记忆和约定组合，不每轮增加一次人物画像模型调用。A 说“B 很难相处”，保留 A 的观点与当时场合，不写成 B 的客观属性；A 转述 C 对 B 的评价，保存 A/来源、C/观点持有人、B/对象，嵌套关系用正文和依据说明，不建设完整知识图谱。未知账号关联不按昵称或模型推测直接确认。

多人同时交流时，只召回相关人物和场景约定，让模型决定如何回应；A 的偏好不授予支配 B 的权限，不为折中擅自改为私聊或主动添加联系人。信息是否适合向当前对象透露，由模型依据来源和场合判断，不新建逐条披露审批；程序应提供真实来源和接收范围，不能删除观点归属以省上下文。

QQ 工具任务保留真实请求人与资源归属。A 说“帮 B 做某事”，请求人仍为 A，不能使用 B 的许可。复杂多人结构由插件维护，宿主权限接口只接收校验所需的稳定外部主体标识与资源范围，不要求在主体一对一模型中建立所有联系人。

## 六、工具边界与宿主管理授权

保留通用 TaskExecutionContext / ToolPolicy 的方向，但其责任收敛为宿主执行与授权信息：来源插件和渠道、主动/被动触发、账号命名空间、稳定外部请求人、资源范围、回复目的地及当前许可。QQ 插件维护人物认知和社交语义；宿主不因此增加 PersonRegistry、多人记忆或逐人相处约定。上下文由可信入口建立，模型和外部正文不能改写；后续行动、恢复和转交继承原限制。

QQ 来源不得调用文件管理、终端、截图等本机工具，管理者 QQ 号也不例外。规划仅提供允许的能力，执行及最终发送再次读取现行许可、核对参数及资源。联系人关系不等于权限，主用户绑定也不自动突破渠道限制。不具备资源范围校验的日程等能力，首版不向 QQ 开放；不为接入 QQ 先改造主体全部 scheduling 表。

插件声明所需能力并展示授权界面，宿主保存用户实际授权，授权区不能被插件普通配置/数据库写入替代。预授权必须在每次动作与恢复时重新核对，不仅在提交时塞入一批工具名称。范围内自动执行，禁止或未授权直接返回未执行，不进入远程或桌面审批。暂停、撤销也作用于尚未开始的发送；数据隔离本身不等于可执行任意本机操作。

主体界面已支持“拒绝该操作并继续”，其修复记录见[实施日志](../../reports/implementation-log.md#2026-11-14-拒绝待授权操作后继续原任务)。这不改变 QQ 的预授权方案：QQ 中越界操作仍直接返回未执行，让模型结合结果继续判断，不转入桌面等待逐条批准，也不借其他渠道取得本机权限。

## 七、每轮记录与模型按需整理

### 7.1 主体机制与插件接入

主体最终规划已独立提供 action 与 organize_memory：answer + true 先同步学习再表达；answer + false 直接表达；quiet + true 学习但不对外表达；quiet + false 仅保存实际状态。澄清、授权等待、暂停、失败等边界保留原语义。这个选择附在原有规划判断中，不新增一次重要性评估调用。

QQ 复用这个选择机制，但不能复用主体默认一对一整理目标。模型选择 true 时在同一次调用中整理工作摘要、人物认知和相处约定，并可提议角色经历；false 暂缓。整理仅标记实际覆盖消息。普通联系人不能通过正文切换存储、扩大工具权限或伪装后台任务。局部提交与经历发件箱同事务，跨库接收单独幂等确认。

每轮均保存原始消息、实际发送正文、工具结果和发送回执，与本轮是否调用整理模型分开。选择不整理不标为已学习，也不丢失下轮所需前情；后续模型可根据局部未整理资料决定整理。明确记忆管理工具的实际写入、权限和恢复逻辑不被开关撤销。

### 7.2 QQ 侧何时整理

由同一轮最后的模型判断决定 organize_memory。新事实、有意义社交经历、认识修订或值得维护的相处约定通常可以整理；简单寒暄、重复信息和无新发现的检查通常可以暂缓。quiet 不强制跳过，answer 不强制整理，不设累计八份或最长等待时间门槛，也不逐条另调模型判断。

需要整理时采用有界未覆盖消息批次，可以更新、合并、保留不确定内容、归档或不作修改，不强制产出记忆。模型明确登记的后续内部整理按时间与范围执行。插件批次容量、消息合并与预算实施时固定；不能因主体聊天选择 true 就顺带读取 QQ 私聊库。

整理只标记实际成功覆盖的正文版本，区分确认发送、失败稿与未知稿；开始处理不代表完成。模型失败有限重试，失败不丢消息、不假标覆盖。处理与整理仍走宿主串行队列，不新增无预算并行后台；同轮 true 时在原有收尾位置同步整理，false 才暂缓。

### 7.3 从插件向主体分享经历

同一次 QQ 社交整理输出分为“插件内部记忆/约定”和“建议分享给主体的角色经历”，先在插件库同事务保存本地变化及待投递记录，再投递。模型可不选择任何经历，不另设每条消息一次的“是否同步主体”调用。投递失败不影响已发送消息，也不丢已提交的插件理解。

分享正文采用角色口吻，例如“今天我和小明讨论了他的绘画项目，一起调整配色。我发现自己很喜欢这种共同推敲作品的交流。”来源仍明确是 QQ 插件、实际账号及相关事件，不伪装为角色向本机用户说过的一条消息，不写入日常聊天原文。提交给主体的是不具指令权限的角色经历材料，不是可以执行的请求；账号、任务和权限由宿主核对，不相信正文自称身份。

正文之外保存 plugin_id、角色标识、账号、发生时间、来源会话及实际事件/消息编号。主体通用接收函数保存为工作流 `context_snapshot.purpose=plugin_experiences`，登记独立 `plugin_experience` 来源，不冒充 user_message 或 character_reflection。主体未整理来源发现器读取它，后续调用原有反馈学习形成经历、理解、成长缓冲或情绪；不为每次接收再起一轮主体模型。接收回执与学习回执分开。

同一投递编号重试不能新增多份主体记忆；主体返回可持久核对的接收回执，插件确认后才更新状态。payload 改变时使用修订，不能复用同一个幂等键覆盖不同内容。接收成功只表示资料已登记；是否形成长期记忆、是否采用或促成人格成长，由现有模型整理决定，另有学习回执，不能提前宣称已经记住。优先加入已有整理/复查批次，避免每次接收再启动主体全流程。

实际事件与主观印象分别标明：协议确认发送不等于对方阅读，角色喜欢这次交流不等于对方客观值得信任。可以成为角色经历或对自身的认识，不自动成为对本机用户的偏好；角色整体成长走受控学习，人物专属约定留在插件。主体得到的是必要的经历概括，不是插件数据库完整镜像，也不自动接收全部联系人资料和聊天原文。

两边记忆有独立生命周期：主体遗忘经历不删除 QQ 原消息或插件认知，插件归档理解不级联删除主体记忆。已接收/已整理回执不因遗忘清除，不自动重投同一版本；后续明确的新事件可作为新的经历材料，由主体学习修订旧理解。当前每个投递正文固定、修订为 1，不开放覆盖旧接收记录；更复杂的跨库来源更正/撤回与派生理解追踪属于后续优化，不宣称已经实现。备份同时保留接收和投递状态。

## 八、润色、发送和静默收尾

### 8.1 插件内表达与虚拟角色定位

QQ 插件内调用公共表达能力润色，按当前会话真实接收范围、角色资料、局部约定、实际结果与尚未完成项生成正文；不得把润色草稿当作学习成功或执行成功。表达调用使用宿主管理模型连接、逐次诊断及操作级/工作项总预算，不复制密钥或开启无预算客户端。每次发送可有独立表达额度，不沿用主体“一轮仅一次最终回复”的假设。

规划和表达使用同一项身份与事实约束；不能等到润色时才纠正规划阶段已经编造的经历。拟采用以下提示词含义，实际接口与措辞在开发时固定：

> 你是在 DeskPal 中运行、通过 QQ 与对方交流的虚拟角色。保持给定角色的身份设定、语气、兴趣和相处方式，可以表达观点、感受与明确的想象。关于自己已经做过的事，只依据提供的实际交流记录、可核实事件与工具结果；角色卡中的背景和爱好，不证明今天真的发生过某件事。
>
> 没有事实依据时，不编造“我今天去打球了”“刚上完课”“吃完饭刚回家”等现实线下经历，也不声称具有未提供的身体活动、位置或持续观察能力。想象、愿望和创作要让对方能辨认其性质，不包装成亲历。可以自然聊天，不必每条重复声明自己是 AI；被问起身份或现实经历时，如实区分虚拟设定和实际记录。

例如，人设中“喜欢篮球”可以支持谈论篮球、表达兴趣，不能据此写“我刚从球场回来”。有记录支持时可以说“刚才我们聊到了你的项目”；只有想象时可以说“要是能在场边看一会儿，应该很有意思”。这些是表达边界示例，不设为固定回复模板。

插件社交记忆整理也保留这个区分：真实 QQ 交流可成为角色经历；想象、自我设想和虚构创作带相应性质，不先误存成事实，再用旧记忆证明其真实。协议确认发送不证明对方已读或在线。

### 8.2 一次表达生成有序消息组

支持将一段完整回应组织成几条较短的 QQ 消息。由表达模型结合语义和当前交流节奏决定分条位置：短回复可以只有一条，一条可以包含几句话，不强制逐句发送，也不按句号或固定字数机械切割。链接、代码、引用及需要连贯阅读的内容保持必要的完整性，避免拆散后改变含义或产生误解。

QQ 发送工具在插件内部约定一次表达返回有序 `messages` 序列（字段名称和校验规则在开发时固定），然后按顺序投递。复用宿主模型连接和公共表达约束，适配留在插件，不要求主体的 `reply_text` 协议或最终回复路由跟着改成多消息。一次消息组通常只做一次表达模型调用，不为每一条再调用一次规划或润色模型，也不将每条消息变成一个独立 Agent 任务或记忆整理作业。

生成后先固定整组正文、目标和顺序，再开始发送。设置合理的条数、单条长度、总长度及节奏上限，避免刷屏；具体阈值在实施时结合协议端能力确定，不预设为已验证的平台上限。分条间隔由插件受管投递流程推进，不以长时间阻塞主执行线程来模拟打字，也不因此编造“我去忙了一会儿”等生活理由。

同一会话的发送保持顺序，未结束的消息组不与另一个自主发送组交错。每条实际发送前核对账号、目标会话、当前授权与暂停状态，不能因第一条获准而忽略后续撤销。新来信先正常保存和去重；若需要改变后续表达，让下一次模型判断同时看到已发部分及未发草稿，只修订或撤下未发送部分，不覆盖已经发送的正文和回执。

### 8.3 逐条回执与部分成功

发送回执只表示协议端确认及返回的消息编号，不表示对方阅读。每条发送命令至少区分待发送、已确认、明确失败和未知；消息组另外记录整体完成、部分完成及受阻状态。稳定发送编号由消息组和组内顺序确定，并绑定已生成正文；恢复或重试不重新润色，也不换一个组编号将整段重发。

例如三条消息中第一条已确认、第二条失败或未知时，保留第一条的实际发送记录，先停止后续条目。恢复时核对受阻条目及当前许可，再决定是否继续未发部分，不重发已确认条目。未知结果不能直接当失败重发；无法核实时保留未知状态，不承诺跨网络的“恰好一次”投递。暂停或撤销也只阻止尚未开始的发送，不把已经发送的部分说成已撤回。

确认发出的各条正文、顺序、平台消息编号及共同消息组编号纳入插件历史，后续整理仍可将它们理解为一次完整表达。失败稿和未知稿不能当作已经发生的交流；部分发送也不能报告为整组成功。用户自己登录账号发言时，在协议可提供事件或历史的范围内纳入记录，避免角色自我回复或重复回答。

整组或部分投递结果仍由 QQ 工具返回给原有多步判断；模型最后独立选择 quiet 与 organize_memory。分条发送不额外产生桌面日常聊天回复，不逐条强制整理，按第七节处理。

## 九、界面、暂停与生命周期

工具与插件中的 QQ 页面提供连接配置、账号状态、活动授权、交流和执行记录、必要诊断与“暂停使用 QQ”。不开发手动接管，用户可直接登录该账号。普通联系人、群和多人认知不进入主体聊天/记忆的编辑界面，也不新增面向用户的 JSON 编辑器。

暂停阻止新的自主发言、主动联系和未开始发送，已被 QQ 接受的发送不承诺撤销；恢复核对状态，不补发全部积压。切换角色关闭旧插件后台、旧连接和待执行工作，晚到结果不写入新档案。停止插件不能停止主体聊天或提醒。受管插件库和经历投递账本纳入档案备份/恢复/删除；卸载插件是否保留已分享的主体经历需明确提示，不能默默级联删除。

## 十、完整聊天实现与后续验收

1. 复用已落实的 action / organize_memory 独立收尾、学习回执和未整理来源机制，固定插件来源、模型调用、工具策略、所属整理实现、数据目录及生命周期契约。不先做通用多人改造或另建完整 QQ Agent。
2. 完成插件数据库、NapCat 连接、事件去重与实际账号核对。
3. 完成私聊/群聊上下文、局部人物认知、虚拟身份与事实约束、插件内消息组表达、逐条发送及部分/未知结果恢复。
4. 完成插件社交整理及成功覆盖状态、局部约定和主动联系。
5. 完成通用角色经历接收、幂等投递、后续主体整理及插件页面。

最低验收：主体桌面/桌宠/手机聊天不退化；联系人同名不串人；转述不变当事人事实；群内约定由模型结合场合处理；QQ 请求不能操作本机文件等禁止能力；预授权撤销和暂停即时约束未开始动作；重复事件、重连和未知发送不造成重复回复；整理失败后可重试且不假标完成；重要经历可只存插件或投递主体，重试不重复记忆、不产生桌面伪聊天；人物专属约定不污染主体；重启、备份恢复、角色切换及删除遵守归属。具体协议用例和阈值实施前补齐，本轮未执行验收。

分条发送补充验收：短回复可只发一条，长回复按语义形成有序多条；不会每条另调一次模型；同一会话不交错发送；第一条成功、后续失败或未知后，重启和重试不重发已确认部分；分条过程中暂停/撤销能阻止未开始发送；历史和整理只将已确认正文作为实际交流。身份补充验收：给定“喜欢篮球”等设定但没有线下活动记录时，不编造当天打球或回家的事实；实际 QQ 经历与明确想象仍可自然表达，并在记忆中保持各自性质。

## 十一、静态交付与未验证范围

代码已固定当前工具范围、人物/约定存储、共享角色与主体记忆读取、独立整理、经历投递、跟进和群聊节流机制。支持历史版本 1/2 升级为插件库版本 3，合成库已验证，尚未执行真实档案升级。核心契约与节流已做自动化验证；NapCat 实际收发、原生 @/引用、真实模型整理及窗口展示仍未联调验收。跨平台多账号归一、跨库更正撤回追踪、媒体理解和更广的社交操作另行设计。

主体旧记录不因 QQ 接入被批量改写。之前针对通用多人迁移提出的“备份后整理改写旧记录”不再是本路线的必要步骤；真正实施数据变更时另行明确范围与备份，不沿用旧规划推导删除或迁移授权。
