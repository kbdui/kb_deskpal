# QQ 插件开发设计与已确认范围

日期：2026-11-09；最近更新：2026-11-12。状态：设计已调整，插件尚未开发。本轮仅修改规划，不修改代码、执行测试、调用模型或操作 QQ。

2026-11-12 最新确认：普通 quiet 默认跳过本轮自动记忆整理；明确登记的后台静默整理任务例外。由此撤回为规避每轮学习而强制新建独立 QQ 执行/收尾系统的要求，执行可复用 Dispatcher / AgentCore，数据和整理目标仍按插件隔离。完整每轮流程、延后材料与自主思考变化见 [安静结束与按需整理确认方案](../companion-model/2026-11-12-quiet-and-memory-consolidation.md)，本规则尚未实现。

本次明确替代此前“先改造主体为通用多人系统，再接入 QQ”的路线：主体保持角色与本机用户一对一；QQ 插件管理自己的社交数据、处理流程与记忆。角色身份与基础人格共用，联系人认知、群聊状态及人物专属约定隔离在插件中。此前的[通用多人方案](../companion-model/2026-11-11-multi-person-integration-design.md)降为历史备选，其中有用的人物与归属设计可以下沉插件，不再作为开发前置或当前实施清单。28/29 日原始讨论不改写，后续明确决定优先。

## 一、目标与首版范围

为当前虚拟角色绑定一个专属 QQ 账号，在明确授权范围内自主交流。首版包含账号连接、私聊、群聊、主动联系和插件内多人记忆。主体桌面、桌宠、手机及 CLI 仍服务同一个本机用户，原有聊天和会话结构保持一对一，不增加主体人物注册表或将 QQ 群放入主体会话列表。

社交拓展单独明确授权。接受好友申请、主动添加联系人、接受群邀请等不能从“允许聊天”或“允许主动联系”推导出来。采用“预先明确授权、范围内自动执行、越界直接不执行”，不开发远程审批，也不让 QQ 任务等待桌面逐条批准。文件、语音、复杂群管理和批量操作不列入首版必交付能力。

## 二、协议端与安装

沿用已选 NapCatQQ / OneBot 11。NapCat 负责登录和协议收发，插件负责社交业务。开发阶段由用户在项目之外自行安装 NapCat 并登录；DeskPal 配置连接参数，测试连接后读取并核对账号编号、昵称和在线状态。填写账号名称本身不是登录；首次登录或状态失效时按协议端要求扫码或验证。具体协议行为以开发时固定的兼容版本验证。

Git 只保存插件代码、配置模板、兼容版本和安装说明，不提交 NapCat、QQ 客户端、登录状态、二维码、Token、实际配置及运行日志。未来打包可以考虑在用户数据目录管理可选协议端，安装、升级和回退不作为首版前置。项目为个人爱好、开源、非商用；这不替代第三方组件的许可，未来捆绑或自动下载仍需核对当时许可。

## 三、坚持插件四部分边界

| 部分 | QQ 插件负责 | 宿主提供或保证 |
|---|---|---|
| 主动行为与事件源 | 连接事件、私聊/群聊消息订阅、社交跟进和联系人主动联系机会 | 受管注册、合并去重、串行调度、预算和档案生命周期 |
| 插件能力 | 读消息、理解交流、范围内社交动作、组织回复、润色发送、社交记忆整理 | 公共模型连接与逐次诊断、受限工具执行、实际授权校验 |
| 额外数据库 | 人物与账号、原始消息、社交记忆、相处约定、发送回执及学习/投递作业 | 插件存储命名空间、迁移与备份恢复、关闭和删除生命周期 |
| 图形界面 | 连接配置、账号状态、授权入口、交流/执行记录、暂停 QQ | 插件页面容器和受保护设置操作接口 |

插件拥有社交数据与局部上下文的组织、工具和整理能力，不把来信提交为主体用户发言。理解、规划和多步工具执行可复用现有 Dispatcher / AgentCore；普通 quiet 在公共收尾边界跳过自动学习，不强制另写一套完整 QQ Agent。共享模型连接、诊断、预算和工作队列，不复制密钥或创建无预算并行后台；真实外部来源、局部资料和权限接入仍需适配，不能只把 QQ 联系人写成 local:user 或伪装主动用户任务。

新链路为：QQ 事件或主动机会 → 插件持久保存与去重、登记可信来源 → 复用执行链结合共享角色资料和插件局部记忆理解/行动 → 插件内润色发送并登记结果 → 模型选择 quiet → 公共收尾保存实际状态并跳过自动学习。插件在明确的后台整理机会汇集未整理资料，选择性投递重要角色经历给主体。

复用 AgentCore 不等于使用主体一对一资料或调用默认主体 FeedbackLearning。普通 QQ 收发 quiet 不自动学习；插件后台整理读取并写回插件库。主体无需新增 QQ 专用最终回复路由，成功、失败和未知结果保留在插件记录，不自动转述到日常聊天。免打扰拦下 answer 不等于模型选择 quiet，不能靠空回复猜测是否跳过整理。

## 四、唯一角色与社交数据隔离

角色卡、身份及基础人格仍由主体提供只读快照。插件不复制出可独立修改的长期人格版本，也不直接改主体 companion 数据库。主体当前包含部分针对本机用户的相处要求，不能将整份习惯、用户理解、私密记忆和桌面历史无差别送入 QQ；开发时应明确公共角色资料读取契约，只提供适用于外部场景的基础人格和必要资料，不为此先把主体改成通用多人系统。

QQ 中对 A 的认识、对 B 的印象、群内临时交流方式、人物专属相处约定、对一次社交的局部反应，均属于插件数据及上下文，不覆盖主体对本机用户的要求。每位联系人不是一个新角色，不复制完整人格。QQ 经历若确实促成角色整体成长，通过受控经历入口和主体后续学习形成变化；“对小明少追问”不能直接成为全局习惯。插件不直接写主体当前情绪；有价值的实际社交经历可以成为主体后续理解和情绪更新的依据。

## 五、插件内数据库与多人建模

拟采用当前角色档案下的受管独立插件数据库，例如插件命名空间内 qq.sqlite3。文件名、DDL 和接口名实施时固定；不将其混入已有 memory/companion/conversation 表，不在有限配置键或有界事件缓存中长期保存聊天。库归属当前角色档案，纳入完整备份、恢复、切换与删除；不是跨角色共用社交库。

| 插件内对象/拟议表 | 主要内容与约束 |
|---|---|
| person / social_identity | 稳定人物编号、称呼、人物状态；账号独立保存 platform、namespace、account_id 及确认依据，一人可有多个账号；同名不合并。QQ 是平台取值，不是人物表专用字段。 |
| conversation / participant / message | 私聊、群聊、已知成员、实际发言者、被引用消息、原正文、确认发出的正文、时间与平台状态；按账号、会话及实际协议编号作用域去重。群不是人物，点名回复不等于只有被点名者能看到。 |
| social_memory / memory_person_link | 事实、自述、转述、角色印象及共同经历的提炼正文、状态、修订、理由、不确定性、实际来源消息；关联来源人、内容对象、观点持有人及参与者。 |
| interaction_agreement | 与具体人物或场景的相处约定、明确/推测性质、持续范围、来源和修订；群聊冲突由模型结合当前场合决定，不新增好感度或数字优先级。 |
| social_work / send_command | 处理工作、输入消息、实际请求人、目标会话、允许范围、行动及发送状态；发送命令绑定稳定编号和已润色正文。 |
| learning_job / message_learning | 整理批次、冻结消息编号与正文修订、输入范围、启动/完成状态、有限重试、整理覆盖；任务开始不等于消息已整理。 |
| host_experience_outbox | 可投递主体的角色经历、来源事件、稳定编号、载荷摘要、修订、状态及实际接收回执；不作简单清空即完成的内存队列。 |

人物认知摘要可按需从有效记忆和约定组合，不每轮增加一次人物画像模型调用。A 说“B 很难相处”，保留 A 的观点与当时场合，不写成 B 的客观属性；A 转述 C 对 B 的评价，保存 A/来源、C/观点持有人、B/对象，嵌套关系用正文和依据说明，不建设完整知识图谱。未知账号关联不按昵称或模型推测直接确认。

多人同时交流时，只召回相关人物和场景约定，让模型决定如何回应；A 的偏好不授予支配 B 的权限，不为折中擅自改为私聊或主动添加联系人。信息是否适合向当前对象透露，由模型依据来源和场合判断，不新建逐条披露审批；程序应提供真实来源和接收范围，不能删除观点归属以省上下文。

QQ 工具任务保留真实请求人与资源归属。A 说“帮 B 做某事”，请求人仍为 A，不能使用 B 的许可。复杂多人结构由插件维护，宿主权限接口只接收校验所需的稳定外部主体标识与资源范围，不要求在主体一对一模型中建立所有联系人。

## 六、工具边界与宿主管理授权

保留通用 TaskExecutionContext / ToolPolicy 的方向，但其责任收敛为宿主执行与授权信息：来源插件和渠道、主动/被动触发、账号命名空间、稳定外部请求人、资源范围、回复目的地及当前许可。QQ 插件维护人物认知和社交语义；宿主不因此增加 PersonRegistry、多人记忆或逐人相处约定。上下文由可信入口建立，模型和外部正文不能改写；后续行动、恢复和转交继承原限制。

QQ 来源不得调用文件管理、终端、截图等本机工具，管理者 QQ 号也不例外。规划仅提供允许的能力，执行及最终发送再次读取现行许可、核对参数及资源。联系人关系不等于权限，主用户绑定也不自动突破渠道限制。不具备资源范围校验的日程等能力，首版不向 QQ 开放；不为接入 QQ 先改造主体全部 scheduling 表。

插件声明所需能力并展示授权界面，宿主保存用户实际授权，授权区不能被插件普通配置/数据库写入替代。预授权必须在每次动作与恢复时重新核对，不仅在提交时塞入一批工具名称。范围内自动执行，禁止或未授权直接返回未执行，不进入远程或桌面审批。暂停、撤销也作用于尚未开始的发送；数据隔离本身不等于可执行任意本机操作。

## 七、每轮记录与按需整理：quiet 跳过、后台整理例外

### 7.1 当前事实与本次决定

当前主体 AgentCore 在正常非澄清轮次中调用绑定的 TurnFeedback.finish，由 ApplicationService 装配为 FeedbackLearning；暂停学习等分支另有跳过规则。该主体路径是同步反馈后再发布回复，并非插件框架天生要求所有任务都整理同一记忆库。

普通 answer 的主体同步顺序继续保留；普通 quiet 改为跳过自动反馈学习，明确后台整理任务即使静默仍执行。这是在公共收尾处根据最终动作及可信任务用途判断，不新增一次模型调用判断是否整理，也不依赖独立插件处理器规避主体收尾。QQ 来信保留真实来源，不调用普通用户入口冒充 local:user，不为使用 quiet 冒充主动任务；也不向外部请求开放 skip_learning / memory_backend 参数。

| 工作类型 | 必须完成的收尾 | 是否调用模型整理 |
|---|---|---|
| 主体普通 answer | 原有同步反馈、回执和最终表达发布 | 沿用主体既有同步顺序 |
| 普通 quiet，包括自主思考及 QQ 工具后安静结束 | 实际结果、任务状态、发送正文和内部成果持久保存 | 跳过本轮自动学习，不标为已整理 |
| 明确后台静默整理 | 核对来源及所属库，保存提炼与覆盖回执 | 执行指定范围的整理，是 quiet 规则的例外 |
| QQ 社交整理作业 | 冻结未整理消息范围，在插件库提交理解与学习回执 | 需要时调用插件整理模型 |
| 向主体投递角色经历 | 核对插件来源和幂等键，接收为有来源的角色经历材料 | 复用主体既有整理/复查机会，不重放一次聊天；确需独立整理时走受管内部作业 |

每次必须可靠记录，和每次必须再花一次模型调用学习，是两个不同要求。实现时需修改 AgentCore 等公共收尾处的自动学习条件，保留普通 answer 的原顺序；此前“无须改收尾，只做独立 QQ 工作项”的提案不再采用。权限、执行账本、明确记忆管理工具的实际写入和恢复逻辑不因 quiet 跳过。未整理来源在后续批次处理，不能把每个 quiet 立即补成一次后台模型调用。

### 7.2 QQ 侧何时整理

回复模型在已有判断中可以附带“本段有值得整理的内容”或“稍后继续跟进”的建议，不为每条消息另加一次重要性评估调用。程序按消息累计、最长等待时间、会话处理完成或已有复查机会组成有界整理批次；这些条件提供检查机会，不用关键词或固定分数决定记忆含义。具体阈值尚待实施时确定，不默认每条群消息触发一次整理。

普通 QQ 发送后 quiet 不等待批量记忆整理，但原消息和发送结果必须先可靠登记。下轮社交上下文包含近期正文和已有提炼，不能因尚未整理丢失前情。插件的明确后台整理作业写入插件库，不能调用默认主体学习后仅靠提示词要求不串库。处理与整理初期仍在宿主管理的串行队列执行，不承诺抢占或并行；这里不改变主体普通 answer 先学习再发布的同步约定。

整理只选未成功覆盖的实际消息版本，可按需要检索已整理历史佐证。一次实际发送的最终正文也有独立覆盖状态；开始处理不能直接标记完成。模型失败有限重试，作业发起与完成分别记录，失败不丢消息、不把整段标为已学习。收到大量群消息时，执行去重、合并、有界输入和公平轮转，而不是增加逐条模型请求。

### 7.3 从插件向主体分享经历

同一次 QQ 社交整理输出分为“插件内部记忆/约定”和“建议分享给主体的角色经历”，先在插件库同事务保存本地变化及待投递记录，再投递。模型可不选择任何经历，不另设每条消息一次的“是否同步主体”调用。投递失败不影响已发送消息，也不丢已提交的插件理解。

分享正文采用角色口吻，例如“今天我和小明讨论了他的绘画项目，一起调整配色。我发现自己很喜欢这种共同推敲作品的交流。”来源仍明确是 QQ 插件、实际账号及相关事件，不伪装为角色向本机用户说过的一条消息，不写入日常聊天原文。提交给主体的是不具指令权限的角色经历材料，不是可以执行的请求；账号、任务和权限由宿主核对，不相信正文自称身份。

正文之外保存 plugin_id、档案与角色标识、插件事件稳定编号/修订、发生时间、来源会话及最小必要参与者描述、真实发送或事件状态。主体使用一个通用“接收插件角色经历”接口，不新增 QQ 专用写入分支或主体人物表。新来源语义应与 user_message、未发布草稿和 character_reflection 区分：插件经历不是自主思考，不能冒用后者规避来源校验。具体来源枚举和 DDL 在开发时确定。

同一投递编号重试不能新增多份主体记忆；主体返回可持久核对的接收回执，插件确认后才更新状态。payload 改变时使用修订，不能复用同一个幂等键覆盖不同内容。接收成功只表示资料已登记；是否形成长期记忆、是否采用或促成人格成长，由现有模型整理决定，另有学习回执，不能提前宣称已经记住。优先加入已有整理/复查批次，避免每次接收再启动主体全流程。

实际事件与主观印象分别标明：协议确认发送不等于对方阅读，角色喜欢这次交流不等于对方客观值得信任。可以成为角色经历或对自身的认识，不自动成为对本机用户的偏好；角色整体成长走受控学习，人物专属约定留在插件。主体得到的是必要的经历概括，不是插件数据库完整镜像，也不自动接收全部联系人资料和聊天原文。

两边记忆有独立生命周期：主体遗忘一条经历不删除 QQ 原消息或插件记忆；插件删除其提炼不自动级联删除主体已接收经历。投递账本保留已接收/已结束状态，不因主体遗忘自动重投同一版本；后续明确的新事件可以产生新的材料。更正或撤回使用明确来源修订与处理契约，不由插件直接改主体表。备份恢复须同时核对已投递状态，不能因单边回退重复登记。

## 八、润色、发送和静默收尾

QQ 插件内调用公共表达能力润色，按当前会话真实接收范围、角色资料、局部约定、实际结果与尚未完成项生成正文；不得把润色草稿当作学习成功或执行成功。表达调用使用宿主管理模型连接、逐次诊断及操作级/工作项总预算，不复制密钥或开启无预算客户端。每次发送可有独立表达额度，不沿用主体“一轮仅一次最终回复”的假设。

发送回执只表示协议端确认及返回的消息编号，不表示对方阅读。发送命令至少区分待发送、已确认、明确失败和未知。绑定稳定命令编号与已生成正文，重试不重新润色成另一条消息；未知先核对，不能直接无限重发。确认发出的正文纳入插件历史和后续整理；失败稿不能当已发生交流保存。用户自己登录账号发言时，在协议可提供事件或历史的范围内纳入记录，避免角色自我回复或重复回答。

## 九、界面、暂停与生命周期

工具与插件中的 QQ 页面提供连接配置、账号状态、活动授权、交流和执行记录、必要诊断与“暂停使用 QQ”。不开发手动接管，用户可直接登录该账号。普通联系人、群和多人认知不进入主体聊天/记忆的编辑界面，也不新增面向用户的 JSON 编辑器。

暂停阻止新的自主发言、主动联系和未开始发送，已被 QQ 接受的发送不承诺撤销；恢复核对状态，不补发全部积压。切换角色关闭旧插件后台、旧连接和待执行工作，晚到结果不写入新档案。停止插件不能停止主体聊天或提醒。受管插件库和经历投递账本纳入档案备份/恢复/删除；卸载插件是否保留已分享的主体经历需明确提示，不能默默级联删除。

## 十、实施顺序与验收

1. 落实公共收尾的 quiet 跳过及后台整理例外、跳过回执和未整理来源发现，再固定插件来源、模型调用、工具策略、数据目录及生命周期契约。普通 answer 保留同步学习，不先做通用多人改造或另建完整 QQ Agent。
2. 完成插件数据库、NapCat 连接、事件去重与实际账号核对。
3. 完成私聊/群聊上下文、局部人物认知、插件内润色发送及结果未知恢复。
4. 完成插件社交整理批次与成功覆盖状态、局部约定和主动联系。
5. 完成通用角色经历接收、幂等投递、后续主体整理及插件页面。

最低验收：主体桌面/桌宠/手机聊天不退化；联系人同名不串人；转述不变当事人事实；群内约定由模型结合场合处理；QQ 请求不能操作本机文件等禁止能力；预授权撤销和暂停即时约束未开始动作；重复事件、重连和未知发送不造成重复回复；整理失败后可重试且不假标完成；重要经历可只存插件或投递主体，重试不重复记忆、不产生桌面伪聊天；人物专属约定不污染主体；重启、备份恢复、角色切换及删除遵守归属。具体协议用例和阈值实施前补齐，本轮未执行验收。

## 十一、尚待实施时确定

授权粒度和具体开放工具清单、公共角色资料快照可包含哪些现有习惯、插件整理批次阈值、独立库 DDL 与迁移、经历接收/更正/撤回协议、页面详细排布及固定协议版本。已确认插件隔离、唯一角色、局部多人认知、quiet 跳过及明确后台整理例外，以及选择性经历投递；不将未定细节当作当前接口或已完成开发。

主体旧记录不因 QQ 接入被批量改写。之前针对通用多人迁移提出的“备份后整理改写旧记录”不再是本路线的必要步骤；真正实施数据变更时另行明确范围与备份，不沿用旧规划推导删除或迁移授权。
