# QQ 插件开发设计与已确认范围

日期：2026-11-09；最近更新：2026-11-11。本文记录已经确认的方向、开发必须补齐的能力，以及仍待讨论的事项；不是实现完成报告。本轮只写文档，不开发插件或操作 QQ 账号。2026-11-11 已确认将润色与发送封装在 QQ 插件内；同日新增的人物认知档案和数据结构评估仍是建议，尚待用户确认。

## 一、目标与首版范围

给当前虚拟角色绑定一个专属 QQ 账号，让它在明确授权和安全边界内自主交流。首版包含专属账号连接、私聊、群聊、主动联系和多人记忆。角色沿用当前档案的唯一人格与记忆，各个 QQ 私聊和群聊维护独立的近期正文和工作上下文。

社交拓展需要单独明确授权，不能由“允许聊天”或“允许主动联系”推导出来。接受好友申请、主动添加联系人和接受群邀请等属于社交拓展。已采纳的授权原则是“预先明确授权，范围内自动执行，越界直接不执行”，不开发远程审批；授权入口和具体范围粒度后续确认。未得到相应授权时不得执行，也不创建等待桌面批准的 QQ 任务。

文件、语音、复杂群管理和批量操作不纳入首版必交付能力。发送结果记录和授权校验属于实现日常交流所必需的基础设施，不另造一套面向用户的复杂管理系统。

## 二、协议端与安装

选用 NapCatQQ 作为协议端，以 OneBot 11 对接 DeskPal。NapCat 负责 QQ 登录及底层收发，DeskPal 插件负责业务适配，语义理解、行动选择、人格表达和学习继续由现有系统承担。具体 API 以开发时固定的兼容版本验证，不假定所有扩展 API 在任意版本均可用。

开发阶段由用户自行安装 NapCat 并完成登录。DeskPal 配置实际连接参数，连接后读取并核对 QQ 号、昵称与在线状态，防止绑定错账号。账号备注和 QQ 号分别保存；填写昵称或 QQ 号本身不是身份验证。已有有效登录状态时可尝试快速登录；首次登录、状态失效或设备验证时，按 QQ 要求完成扫码或其他验证。

协议端安装在 Git 项目之外。Git 仅保存插件代码、配置模板、兼容版本及校验清单、安装说明；不提交 NapCat 和 QQ 客户端程序、登录状态、二维码、Token、实际配置及运行日志。未来安装包可考虑在用户数据目录管理可选组件的安装、启动、升级和回退，首次登录可在 DeskPal 内展示登录入口；本次不实现组件管理器，也不要求开发阶段先达到一键安装体验。

用户明确说明 DeskPal 是个人爱好、开源、非商用项目。这记录项目用途，不等于已经取得第三方组件的额外授权。未来是否捆绑分发或提供自动下载安装，仍须按当时 NapCat 及所含依赖的许可核对。

## 三、插件结构与处理链路

沿用四部分插件设计：可调用工具、可订阅事件源、受管持久存储、前端操作页面。协议连接与人格运行解耦，QQ 不另起一套规划、学习或主动聊天模型。

已确认的新链路为：QQ 事件接收 → 保存和去重 → 统一事件入口 → Submission Dispatcher → AgentCore → 人格与记忆及允许的工具 → 模型调用 QQ 发送工具 → 插件内调用模型润色、发送并登记实际正文 → 结果回到原执行链 → 按现有规则整理记忆并静默收尾。

QQ 的回复组织与交付由插件封装，不再采用“主流程结束前统一生成最终表达，再新增渠道路由将其转发 QQ”的旧方案。插件内复用公共的角色上下文、表达能力和任务绑定模型调用接口，不复制一套人格、规划、学习系统，也不直接读取模型密钥另起无预算的客户端。既有多步执行继续由 AgentCore 负责；工具执行后仍可依据结果决定下一步。

宿主仍需补齐通用任务来源、权限及呈现边界：QQ 来源任务不在桌面聊天页生成最终回复，完成、失败和结果未知显示于插件记录。呈现方式由可信入口登记并随恢复保留，不能只等模型自行选择 quiet，也不能为使用 quiet 将所有 QQ 来信冒充为主动任务。该边界供其他插件复用，不增加 QQ 专用的主流程发送分支；任务来源、主动/被动触发与呈现方式分别处理。

消息通过事件订阅接收，不反复调用模型检查“有没有新消息”。程序负责连接、事件收集、合并、去重、调度与频率预算；模型判断是否回复、如何回复、是否跟进或安静结束。主动联系复用统一主动行为机制，避免为 QQ 硬编码另一套主动行为流程。普通群消息可合并处理，不能每条群消息都无条件触发模型调用。

当前插件状态存储适合少量配置，事件每源仅保留最近 500 条，页面主要支持开关和信息列表。因此完整 QQ 插件开发需补齐通用连接生命周期、受管消息与发送存储、插件页面操作能力；不能把长期聊天记录塞入有限配置字段或把事件保留窗口当作历史数据库。新增持久存储必须纳入档案关闭、备份、恢复和删除流程。

## 四、QQ 来源任务的工具边界

QQ 来源的请求不得调用文件管理、终端、截图等本机操作工具。此限制包括绑定为管理者的 QQ 号发来的请求，不能因为对方是本机用户就自动突破渠道边界。

规划阶段只向模型提供 QQ 场景允许的工具；执行阶段再次校验宿主记录的任务来源和能力范围，拒绝模型自行构造的越界调用。后续规划、追加要求、恢复、主动跟进以及内部转交任务必须继承限制，不能换一个入口就取得更大权限。外部消息正文、昵称、自称身份和模型自行声明均不能修改这些宿主权限。

身份和权限分别处理。联系人可与角色聊天并形成记忆，不自动获得应用设置、全局人格管理、他人记忆删除或其他本机管理能力。首版具体可用工具清单与社交动作批准策略仍需在开发前确定。

### 已采纳的通用宿主架构

`TaskExecutionContext` 和 `ToolPolicy` 放在宿主，作为其他插件也可复用的通用能力。前者由可信入口生成并随任务持久保存来源渠道、触发方式、实际发言者、角色账号、会话、允许的回复目的地及桌面呈现方式；这些信息供插件发送工具和宿主权限检查使用，不意味着宿主要实现 QQ 发送路由。任务来源与回复去向分别记录，模型不能修改来源或自行增加权限。主动任务、后续轮次、恢复、追加要求和子任务继承原限制。

插件声明所需能力和账号、联系人、群等资源范围，提供相应范围的校验方式。宿主保存用户实际授予的权限，每次具体调用核对工具和参数。插件页面可以展示授权入口，但授权写入必须经过宿主的设置接口，保存在插件不能自行写入的受保护授权区，不能放到插件能任意 `set_state` 的普通配置中。授权按当前角色档案、插件和账号归属保存，不让同名账号或其他档案借用。

宿主在规划时筛选工具，在工具真正执行和最终发送前再次核对当前授权。插件提供的范围规则可以进一步收紧许可，不能推翻宿主禁止项。禁止、未授权、撤销与暂停均返回未执行结果，QQ 不进入远程或桌面逐次审批状态；桌面任务仍可保留既有确认方式。持续许可不能仅作为一批工具名塞入提交时的内存授权，因为现有多轮执行会消费并清空单次授权；应在每轮、每次动作及恢复后重新读取并校验宿主保存的许可。当前为已确认的开发设计，尚未实现。

## 五、多人记忆的必要补齐

现有 `MemorySource` 已有来源类别和可选的发言者编号、称呼、参与者类型、渠道；`MemoryDraft.subject` 表示内容对象。底层可保存同名不同人的身份，但普通学习入口仍以本机用户为默认对象，检索主要按文本相关性排序，不能据此声称已经具备长期稳定的多人运行能力。

开发 QQ 插件时必须贯通以下边界：

- 以宿主提供的稳定 QQ 身份识别人，不按昵称或群名片合并；同一人的不同群名片也不重复创建身份。
- 消息写入、学习材料、记忆对象、检索、更正与合并均携带实际人物和会话范围，不把 QQ 联系人写成 `local:user`。
- 区分某人的自述、他人对他的转述、角色自己的印象和双方实际形成的约定。
- 某位联系人的称呼或相处偏好只在适用范围生效，不改变对其他人的称呼，也不制造人格版本切换。
- 同名者、多人同时交流、群聊引用、跨会话提及、记忆更正、重启恢复及持续增长需要定向验证。
- 组织上下文时保留发言者、内容对象、来源和当前接收者。资料是否适合向某人透露，由模型结合这些信息判断；程序不通过关系亲疏规则或关键词预判可否透露，也不为此另设人物间的逐项信息披露许可。

这些工作是首版“多人记忆”的组成部分，不作为以后再修的显示问题。不能仅靠给模型一句“不要认错人”来保证正确归属。

### 已采纳的多人关系实现架构

宿主增加可复用的 `PersonRegistry`，保存稳定人物身份及其平台账号关联。人物表与平台身份关联分别建模；昵称、群名片是可变化的显示信息，不是合并依据。同一 QQ 账号在不同群中的名片归于同一个人物，不同账号即使同名也分别保存。跨平台身份只有经过可靠确认后才关联，模型可以提出待核对理解，不能自行修改账号绑定或管理者身份。

关系内容继续放在原有记忆系统中，不另建好感度分值或一套重复的关系事实库。语义记忆保存人物自述、转述与关系事实；情景记忆保存有意义的共同经历；角色的印象和理解保留来源及不确定性。区分“谁说的”“内容主要说谁”“涉及哪些人”，新增轻量的记忆—人物关联索引，支持一条经历涉及多个参与者。索引随记忆修订更新，遗忘时一并清理，正文和事实权威仍由原记忆记录承担。

角色保持唯一长期人格。某位联系人的称呼与相处约定标明适用人物或会话，组织上下文时只采用适用于当前交流的要求，不为每位联系人复制人格。`CompanionRuntime.context()` 需要加入当前交流对象；旧记录中适用对象不明确的习惯由模型复查归类，不能自动推广到所有联系人。

当前请求的交流上下文携带实际发言者、会话、涉及人物和接收者。检索先确定当前人物、被明确提及的人及有关共同经历，再比较内容相关性；这用于正确归属和控制输入体积，不由程序猜测某条资料适不适合透露。最终是否向对方转述由模型判断。学习模型只引用宿主提供的真实人物编号，程序验证身份存在与来源有效；更正、去重与合并必须核对人物，不能因内容相似而把不同人的记录混为一条。

具体落点为：`PersonRegistry` 管理身份；`TaskExecutionContext` 携带任务中的真实交流对象；`MemoryRepository` 管理人物关联；`MemoryRetriever` 按人物和话题检索；`FeedbackLearning` 提炼与复核多人内容；`CompanionRuntime` 组合唯一人格与当前对象适用的相处要求。关系含义及变化仍由模型理解，程序不根据聊天次数自动授予“朋友”身份或工具权限。

### 2026-11-11 新讨论：人物认知档案与通用社交账号（评估，待确认）

用户提出：不仅登记人物身份，还应建模虚拟角色对每个人的了解、印象及相处方式；平台账号也应泛化为社交账号，不将 QQ 编号作为人物模型的专用字段。建议采纳业务方向，但身份与会变化的理解分开保存，通过统一的人物档案视图呈现，避免将关系事实再复制一份到注册表。

人物档案表示“当前角色如何认识这个人”，随角色档案的整套数据库隔离、备份、恢复、删除而切换，不另建跨角色共用的认知库。它不是给每位联系人复制一个角色人格。可以先认识一个没有社交账号的人，例如用户在聊天中提到的同学；QQ 群属于会话或场景，不作为一个人物。对同一人的认识和相处方式由模型逐渐更新，理由由模型维护，原消息及记忆修订关联由程序保存。

| 档案内容 | 建议存放与用途 |
|---|---|
| 人物身份 | `PersonRegistry` 保存角色档案内稳定 person_id、显示称呼与必要的身份关联。注册表负责认人，不将推测变成身份事实或管理权限。 |
| 社交账号 | 独立账号关联表，一人可有零个或多个账号。保存 platform、namespace、account_id 等平台无关信息；QQ 只是 platform 的一个取值，account_id 用字符串。namespace 用于平台规定的租户、服务或账号内身份作用域，按实际协议确定，不靠昵称构造。 |
| 关于这个人的事实、印象和推测 | 继续使用长期记忆和不确定缓冲，记录主要对象及相关人物，区分自述、转述、观察和角色假设。 |
| 共同经历 | 继续使用情景记忆，一条经历可关联多个参与者及同一段原始交流，不为每个人复制全文。 |
| 与这个人的相处方式 | 在现有人格学习记录中加入适用人物或会话范围，例如对小明少追问、对小红解释详细。通用人格习惯仍是同一份；对某人的适应不自动推广到所有人。 |
| 人物认知摘要 | 按需汇总以上有效资料，例如“我认识的小明、我们最近在处理什么、目前怎样与他交流”。需要缓存时保存依据与修订，可重建；摘要不是第二份独立的事实或习惯真相。 |

“社交账号”不宜只是人物表的单个字符串字段或任意 JSON 账号列表。独立关联表便于一人多平台、多账号及稳定去重；同一个受作用域限定的外部账号只能有一个明确的人物归属，未知关联暂不合并。QQ 好友备注、群名片和平台昵称作为显示资料保留，同名不合并。跨平台“可能是同一个人”可进入待核对理解，可靠确认后才改变账号关联；社交账号关联也不自动等于本机用户或管理者授权。

人物认知可以是“他最近很忙”“他可能更喜欢先被倾听”“我们因某次共同经历熟悉起来”，由模型维护理由和不确定性，不固化成一组好感度、信任分或性格轴。首版可以直接组合已存在的相关记忆和相处要求，不要求每轮再调用一次模型生成完整人物档案；后台整理确有必要时再顺便维护简短摘要，避免因联系人增加而平白增加每轮调用次数。

相处方式需同时表达“对谁适用”和“持续多久”：person_id/会话决定对象范围，turn/conversation/day/persistent 决定时间范围，不能把现有 scope 字符串当作已经具备人物隔离。多人群聊中先知道实际发言者、被提及者、参与者和接收者，再由模型选择当前交流方式；不把所有联系人的要求一次性拼进提示词，也不按固定好感度或聊天次数决定关系。

这不要求新增“关系记忆”类别。此前划分保持成立：事实和知识属于长期记忆，有意义交流属于情景记忆，角色惯常思考方式属于唯一人格，对某人的适应是有适用范围的相处方式，当前话题属于会话工作上下文，实时任务与安排及工具明细仍由各自服务负责。角色当前情绪继续是一份与事件有关的角色状态，可以关联涉及人物，不为每位联系人复制一套情绪或人格。

### 对现有数据与流程的影响（评估，待确认）

当前 `MemorySource` 已有 speaker_id、speaker_kind、channel 等来源元数据，但没有稳定人物注册与多账号映射。`MemoryDraft.subject` 只有一个文本值且默认 user，不能直接覆盖一条多人经历；`PreparedTurn` 没有当前人物、参与者和接收者的专门结构。`CompanionRuntime.context()` 当前主要按时间、本轮和会话筛选习惯，不按人物筛选；人格存储也将习惯等层各限制为 64 条，不能简单把所有联系人的习惯塞入现有全局列表后声称支持长期多人使用。

| 部分 | 建议调整 | 不应误认为已经具备的能力 |
|---|---|---|
| 人物及账号存储 | 新增档案内人物和外部账号关联的持久存储、唯一约束及确认后的关联维护。注册表由宿主管理，插件提供可信平台身份，不能自行指定管理者。 | 将 speaker_id 拼成 QQ 号字符串，并不等于已有可靠人物管理。 |
| 消息与来源 | 保存发言者的规范人物编号、原始平台身份和渠道；消息有稳定编号，角色实际发出的 QQ 正文也进入已发布发言记录。 | 不应覆盖聊天原文，也不靠昵称重新推断历史发言者。 |
| 记忆人物关联 | 引入与记忆修订关联的人物索引，区分主要对象、共同参与者及被提及者；来源的发言者与内容对象仍分开。无人物对象的通用知识允许为空。 | 不将每条知识硬塞给某个人，不为多人经历复制多份正文。 |
| 现有 subject | 将其作为旧版兼容信息梳理；人物归属迁移为真实 person_id 及关联索引，并明确唯一的权威写入方式。可保留非人物主题含义，但不长期维护 user 文本与人物编号两套互相矛盾的归属。 | 不能直接把所有旧 subject=user 改成最新 QQ 发言者。 |
| 人格与相处约定 | 为人物专属要求加明确目标范围，按人物检索和分页持久保存；不再用当前 64 条全局内存列表容纳所有联系人的长期要求。 | 不是每人创建一张角色卡或复制长期人格。 |
| 会话和临时上下文 | 当前请求携带发言者、相关人物、参与者、接收者及会话场景，短时要求仍按会话与当前交流范围生效。 | 不让一个群里的临时倾诉需求覆盖另一个会话的工作方式。 |
| 检索与学习 | 人物和当前话题共同决定召回；模型输出的人物编号须属于宿主提供的真实人物，采用、合并、更正同时核对人物及来源。已有共用缓冲和复查机制继续复用。 | 仅增加人物字段、不贯通检索和学习，仍会把不同人的事情混在一起。 |
| 备份、清理与摘要 | 人物关联、账号、人物专属习惯纳入档案生命周期；遗忘记忆清理其关联和派生缓存，保留聊天原文。账号解除关联不自动删除这个人的全部记忆。 | 缓存不能成为遗忘后旧理解重新出现的独立来源。 |

建议把人物事实及情景正文继续放在 memory 数据库，把人物专属相处要求放在 companion 数据库，人物身份注册归宿主的档案级持久化模块；具体表位置和迁移版本实施前统一确定。现有部分正文使用 JSON 存储，加入字段在技术上不一定新增列，但人物索引、账号唯一约束、习惯检索和生命周期仍需要正式数据库设计及升级，不能仅靠“JSON 可以塞更多字段”替代这些工作。若跨数据库投递，复用现有带来源和幂等检查的学习投递机制，不做无回执的双写。

派生的人物摘要缓存随依据修订失效后重建，不自动删除其他独立记忆或人格。这里不扩展为“更正一条记忆后由程序猜测并改写所有相关理解”；理解之间更广泛的修订仍交给已有模型复查机制，遵守此前确定的范围。

总体难度为中等偏大，主要成本在认人、记忆归属、人物专属相处方式、群聊上下文和修订一致性，而非 QQ 协议本身。可按“人物/账号及稳定身份 → 消息和记忆人物关联 → 人物范围内相处要求及检索学习 → QQ 事件与发送集成”的顺序实施；先用桌面合成多人场景验证，降低把身份错误和连接错误混在一起排查的成本。这些是本次评估建议，尚未视为用户已确认的新增实现约定。

### 旧记录的处理方向

用户说明当前旧记录不长，可以考虑先备份再直接整理改写。实施时先在后台安全停止后保存完整角色备份，覆盖工作流、记忆、安排、人格及受管资源；同时保留开发前代码基线。由模型结合旧记录与真实消息来源提议人物归属和约定范围，程序核对真实身份、来源和修订后写回，缺少依据的不猜测归属。

直接整理适用于提炼后的记忆、相处约定和必要索引，不改写用户与角色的聊天原文。旧来源保留未知身份，不能仅凭称呼强行映射到某个 QQ 账号。备份验证和具体改写安排属于后续实施工作，本次只记录方案，没有备份或改动真实数据库。

## 六、插件内润色、发送与静默收尾

QQ 消息的接收和回复不走桌面日常聊天界面。模型决定调用 QQ 发送工具时，插件先通过公共表达能力再次调用模型润色，再把实际正文发送到核对后的 QQ 会话；不直接发送未经润色的规划草稿。发送后结果回到原执行链，主流程不再额外润色或发布一份桌面回复。此方案替代旧的主流程最终表达后统一路由方案，目的是将 QQ 能力封装在插件内，避免主流程随每个渠道增长发送逻辑。

润色输入应包含当前角色、适用的相处要求、相关记忆与实际会话上下文，回复对象由可信上下文和授权范围确定，模型不能通过润色改换收件人或扩大权限。润色调用计入该任务模型预算，失败不发送；复用公共表达实现和基本约束，QQ 只补充适合该渠道的表达要求，不能另维护一套逐渐漂移的人格规则。

发送在工具执行期间完成，通常早于本轮后续的记忆整理。因此润色不能声称尚未完成的学习已经保存。实际发出的正文与对方消息应作为带真实发言者、渠道、会话及消息编号的已发布交流保存，进入后续上下文和学习；规划草稿不冒充实际发言，不能只保留可能被截断的工具结果摘要。后续是否继续工具操作仍由原多轮执行链根据真实发送结果决定。

不发桌面回复由宿主通用呈现边界保证，不把“模型这次记得返回 quiet”当作唯一条件。主动联系与收到消息后的回复分别保留原触发语义，QQ 来信不借用主动任务身份；主动联系的授权、暂停和对外发送检查在实际发送前再次执行。QQ 发送失败或结果未知也不会自动向桌面日常聊天转述对方内容，而是在插件页保留可查看状态与执行详情。

“发送回执”指协议接口是否确认发送成功及返回的消息编号，不代表接收者已经阅读。发送记录至少区分待发送、已确认发送、明确失败和结果未知。重连和事件重复投递需去重；发送超时不能直接假定失败并无限重发。能核对时核对，不能确认时保留未知状态，不声称已经送达。

同一个发送命令对应稳定编号及已生成正文，重试不能重新润色后当作另一条消息发送。已确认发送不再重复执行；结果未知先核对发送记录，不能因为主流程恢复或模型再次调用同一工具而重复发出。插件同时区分模型自主发送和用户直接登录账号发言，避免把自身发送回流事件再当作新的来信回答。

“授权范围”指用户允许哪些操作、哪些联系对象以及是否允许主动联系；它与发送回执是两个概念。日常交流、主动联系、社交拓展不得互相隐含授权。2026-11-09 已确认：预先明确授权，范围内自动执行，越界直接不执行，不开发远程审批。插件启用时授予的活动许可由宿主持久保存，每次执行重新校验；模型不能扩大许可，授权撤销与暂停也必须对待执行的发送生效。禁止的本机能力不提供临时批准入口，未获授权的动作返回未执行结果，不挂起等待用户从桌面批准。

## 七、页面与暂停

QQ 页面放在工具与插件中，提供连接、账号状态、必要设置、交流或执行记录，以及“暂停使用 QQ”。不开发“手动接管”功能；用户可直接登录角色账号处理事情。

暂停后阻止新的自主发言、主动联系及尚未开始的发送动作，不能只隐藏页面而让后台继续发。已经由 QQ 接受的发送无法承诺撤销。恢复时核对状态，不自动补发全部积压内容。用户直接登录账号发出的消息，在协议端可提供事件或历史时应纳入对应会话，避免角色重复回答。

角色切换沿用档案隔离方案：旧角色后台关闭，旧 QQ 适配活动停止；新档案核对自己的账号绑定，不让旧连接或晚到结果写入新档案。

## 八、当前仍待确认

日常活动和社交拓展的具体授权粒度；首版插件页面的详细排布；协议版本、具体存储迁移和验收用例；旧记录备份及整理改写的实施安排。2026-11-11 新提出的人物认知档案、通用社交账号与关联数据调整，当前为待确认的评估建议，不能把上一版身份注册设计的已采纳状态扩大到这些新细节。

已确认：插件内调用公共表达能力润色并发送，宿主通用呈现边界静默收尾，替代主流程最终表达后新增 QQ 路由；通用任务上下文、工具策略、宿主管理授权及此前多人身份、人物关联与唯一人格原则；资料是否适合向对方透露交给模型判断。本文仍是设计记录，尚未实现插件。
