# P5 开发：主动检查、记忆整理、通知与任务暂停

日期：2026-10-29。状态：代码与定向隔离验证完成，真实模型效果及原生实机未验收；实际结果见[实施记录](implementation.md)。依赖 P1–P4；[公共架构](../architecture-and-contracts.md)，[本阶段验收](acceptance.md)。

2026-10-30 补充：本阶段增加用户主动暂停／继续多步任务，依据[执行与生命周期决定](../../../design/companion/execution-lifecycle-decisions.md)中的手动暂停规则。此能力在 P5 新增，不作为此前 P3 的交付事实。

## 目标与边界

在现有 `proactive` 包基础上建立一个协调器和少量可增删的内置触发方法。应用服务管理生命周期，触发器报告检查机会；模型决定含义，既有服务执行。正常主动能力默认可用，不以日常人工候选审核或默认关闭替代体验设计。

| 动作 | 执行原则 |
|---|---|
| 已约定提醒 | 调度按时履约，不因模型临时不可用而取消承诺。用户要求暂停提醒时由通知策略实际控制。 |
| 普通主动聊天 | 协调器提交主动交流任务，经 Dispatcher 进入 AgentCore，由模型结合角色、记忆和有效要求决定说、推迟或安静，不先堆到审核页。 |
| 外部实际操作 | 进入既有任务、工具与授权链，不因主动性而放宽权限。 |
| 内部记忆整理 | 提交 P4 反馈整理工作；模型决定保留、合并、修正或清理，记忆服务落实，不要求每次发消息。 |

## 代码入口

`proactive/engine.py`、`manager.py`、`models.py`、`application/service.py`、`dispatcher.py`、`reminders.py`、`scheduling/*`。P4 反馈入口、记忆服务、统一网关及发布入口复用。现有目标、里程碑、日程绑定的可靠事件能力继续保留，不把所有事件来源重新实现。

任务暂停还涉及 `agent/core.py`、`workflow/*`、应用层任务控制接口与主窗／小窗调用方。复用已有追加要求接收、任务状态、执行账本和持久上下文，不另建执行 Agent；如需扩展数据库，通过正式版本迁移完成，不靠服务临时建表。

## 检查机会及记录

内置新事件触发、模型安排复查、合适表达机会、低频兜底四类。随机性仅在有理由的时间窗口内少量错开，不作为主要唤醒机制。没有应用消息不能推断用户空闲，不新增屏幕或摄像头采集。

检查项最少保存：当前档案、关注对象、简短理由与真实来源、时间窗口或条件、取消条件、触发方法、有效状态及必要修订。是检查安排，不是另造一份目标或长期事实。用户无需填写或审计这张记录。

同一事项的短时间事件先合并，再调用模型。去重、调用预算、间隔、重试上限与关闭恢复由程序保证；是否有意义、如何回应和何时再想交给模型。具体时间与预算取内部配置并在实施记录中说明，不向用户暴露复杂规则表。

## 执行路径

1. 来源触发器提交机会，不自行调用模型、改记忆或发消息。
2. 协调器核对档案激活、暂停状态、已有交流、来源有效性和预算，合并或延期；符合条件才登记工作。
3. 需要整理则排入调度器调用 P4；本轮同步提炼仍在原主链路收尾，不能被这个排队替代。集中整理串行、无抢占；开始后不自动让位。
4. 需要主动交流则提交标明来源、目标和真实依据的主动任务，经 Dispatcher 进入 AgentCore。由 Core 使用统一上下文及模型接口判断，可安静、结束关注、安排下次检查、生成消息或继续调用工具；协调器不另行先调用模型生成一份回复再让 Core 重做。
5. 真正发布前重查暂停、档案后台代次、过期和重复状态；晚到结果不能绕过新生效的控制。
6. 发布及检查完成可靠记录；恢复从记录继续，不补弹全部停用期间消息。

主动任务与用户任务复用 Core 和执行账本，但来源与许可不同。不能将关注事项拼成虚构的用户要求；工具范围和权限由程序按任务用途及已有许可落实，不因“主动建议有益”自动获得修改安排或外部操作许可。纯内部整理不为复用链路而绕入 Core，约定提醒也不因此改成模型任务。

主动交流需要学习时沿用同步收尾，在提交和实际发布前调用反馈模块；其自生成内容不构成新的用户事实。模型选择安静时可正常结束并保存必要状态，不发布空回复、假用户消息或冗余完成通知。发布前的暂停、档案及去重检查仍是统一出口职责。

## 通知与打扰控制

由聊天和快捷入口调用同一策略服务，区分普通主动聊天与约定提醒。当前档案中“今天别主动找我”暂停主动聊天，提醒照常；“连提醒也暂停，明早八点恢复”写入提醒暂停与恢复时间。系统通知权限仍由系统决定，不假装模型改了 OS 权限。

暂停不删除日程，也不取消任务。到期恢复由后台运行时落实，档案重新打开时核对已过的时间；未激活档案不运行独立计时线程。提醒生成、收件箱和外发应有明确分层，暂停期间的事项可记录实际状态，但不能偷偷弹出再标已读。

新增触发方法只增加对应实现及注册，删除方法要撤销其未处理检查，不删除真实日程、执行记录或已形成记忆。不要提前建设复杂插件框架。

## 多步任务的暂停与继续

这项能力控制具体任务，与上一节的主动聊天／提醒策略独立。聊天发起的明确控制与快捷按钮进入同一任务控制服务；暂停请求沿独立入口及时登记，不排在被暂停任务之后等待执行，不依赖正在忙碌的模型先理解才能生效。含糊的自然语言要求仍由模型理解归属，不用关键词匹配伪造语义判断。

1. 校验当前档案、后台和任务归属，以可去重的请求记录暂停意图，显示“正在暂停”。终态任务如实返回已结束，不伪造暂停成功。
2. 不强行中断已开始的模型／工具调用，不逐工具抢占；已决定的步骤组可以完成。到下一次模型判断前检查标记，保存已完成步骤、真实结果、上下文引用、待采用追加要求、授权等待及累计预算，再标记“已暂停”并释放执行线程。持久状态提交失败不得假报已暂停，也不得丢失执行事实。
3. 已暂停任务不继续规划或执行；调度器可以处理其他工作，不保持数据库事务、锁或执行线程等待用户。原有取消、权限及有效性检查照常执行，已暂停状态在重启／切回原档案后仍保留，不自动续跑。
4. 用户明确恢复后，同一任务重新进入原调度器，以最新有效上下文、真实执行结果及未采用追加要求返回模型判断。已完成步骤不重放，原累计预算不重置；旧授权只适用原已展示操作，待确认操作不能因恢复自动获准。恢复时重新核对来源及会话有效性，不绕过清空／遗忘边界。
5. 暂停期间允许追加要求，但不自动恢复。取消可终止暂停任务，取消后不再按暂停恢复。重复暂停／恢复、并发取消与晚到结果须通过持久状态及去重控制，不得创建重复执行者或将终态改回运行。

正常收尾已经开始且后面没有下一次行动判断时，允许按既定同步顺序完成并如实显示终态，不强行暂停 P4 整理。暂停不撤销已完成操作，不触发最终完成回复；必要状态反馈不能冒充任务完成。恢复不是新任务，不能靠创建新任务规避执行账本或权限。

此处只实现用户明确控制，不增加后台学习自动让位或新聊天自动抢占。用户看到的“正在暂停”不承诺立即停止外部影响；主窗和小窗应显示相同实际状态，并区分任务暂停、授权等待与通知免打扰。

## 反馈整理与遗忘

主动模块只提供机会，反馈模块负责本批资料的模型复核，记忆服务执行结果。同一待复核记录没有新信息时不反复请求模型；重要不确定项可继续保留。不得用定时器固定清掉所有低置信度或旧记忆。

用户明确遗忘仍走当前任务，不等到定时整理。自动整理可按已确定留存范围清理误提取、重复或失去价值的记录，不能顺便清空原聊天、删除档案或取消日程。清空聊天也不通过主动整理间接删除长期记忆。

## 失败与完成条件

模型失败可按有限规则稍后再试，过时则停止；既有可靠提醒不依赖此模型重试。触发任务和自身发布事件不能无限互相唤醒，沉默不解释为拒绝或催促需求。

交付触发方法清单、检查项契约、通知策略接口、任务暂停／恢复接口与持久状态、恢复行为及 P5 验收记录。只有当前档案运行，普通聊天不需审核，所有内外部动作都能查实际状态，无重复消息、无绕过通知或任务暂停，才进入 P6 整体验收。


## 2026-10-30 补充开发：所有模型复查共用关注链路

依据[补充确认](../../companion-model/2026-10-29-redesign-follow-up-decisions.md#十一2026-10-30-补充确认任务上下文统一复查与情绪变化)，attention_schedule 与反馈 followups 使用同一关注存储，区分 internal 维护与 chat 交流；情绪、习惯、记忆及未决事项共用机制，不要求每条复查都是长期记忆。内部维护到期经唯一 Dispatcher 调用 P4，传入原目标和有效真实来源，不发虚构用户消息；普通主动交流仍进 AgentCore。聊天免打扰不阻断内部维护，停用角色或对应触发方法仍停止其工作。

后台兜底从全部符合条件记录选择有界批次，到期、变化与公平轮转共同考虑；触发时冻结目标标识及修订，执行不另选。覆盖修订与尝试时间分别持久记录，避免最新记录独占与遗漏到期事项。间隔、单次条数、重试及同一来源重新安排预算继续有效，不能因情绪未解决而无限唤醒。本轮内部边界为每批最多 16 条、自动批次间隔至少 15 分钟；未被处理的同一修订最多自动选入三批，达到上限只停止无变化的兜底重试，不删除或假记已确认，出现新修订后可再评估。同一来源一天最多重新安排四次，模型失败仍沿用每工作最多三次调用。旧 P5 证据不代替本补充验收。
