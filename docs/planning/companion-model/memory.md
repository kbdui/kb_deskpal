状态：2026-10-14 设计提案，所有新增模型、接口和参数均未实现。总体约束见[设计总览](README.md)，验收见[集成与验收](integration-and-acceptance.md)。

## 1. 分层与所有权

| 层 | 内容 | 保留方式与使用边界 |
| --- | --- | --- |
| WorkingContext | 当前输入、必要近期对话、当前任务证据、已选记忆 | 进程内、会话隔离、预算限制；会话结束或临时模式退出后释放 |
| SourceEvent | 原始用户陈述片段、工具结果白名单字段、确认/更正事件 | 最小化持久证据；角色、来源、时间不可由模型改写；不等于全量聊天库 |
| EpisodicMemory | 一次任务/互动发生了什么、成功/部分成功/失败 | 引用事件；描述实际结果，不将未执行计划写成已发生 |
| SemanticAssertion | 用户自述、偏好、外部说法和可核验观测 | 原子断言、有适用范围和有效期；可更正、争议、归档 |
| DerivedView | UserProfile、RelationshipProfile、跨事件摘要 | 带依赖版本、可重建；失去证据立即失效，不能成为循环自证来源 |

旧 `MemoryKind` 暂保留兼容。WORKING 不再意味着必须写 SQLite；GOAL 仅为 V0.4 GoalManager 的引用/历史快照，不能作为目标状态权威；RELATIONSHIP 表示互动约定相关记录，不表示好感值。暂不另建“技能记忆”：受信工具代码和操作规范由版本管理维护，模型总结的经验最多是待核验建议，不能自动变成可执行代码。

V0.3 的 WorkingContext 需新引入明确 session_id 与有界近期轮次，补足目前 Core 只接单次 request 的边界；不因此承诺跨重启恢复完整聊天/任务。owner_id 先采用本地单用户命名空间，不能宣称已有多用户认证或操作系统级隔离。来源角色、owner/session 均由 Application 赋值，不由 LLM 返回值决定。

## 2. 数据契约

以下是逻辑对象，允许同库实现，不要求每个对象对应一个服务或数据库。

### SourceEvent

必要字段：`event_id/source_revision`、`owner_id`、`session_id`、可选 `task_id/call_id`、`event_type`、`origin`、`speaker`、`occurred_at`、`recorded_at`、`payload_version`、`payload`、`sensitivity`、`retention_policy`、`external_use_policy`。使用独立稳定 event_id；Task 重启丢失不影响已保存来源。payload_version 是格式版本，source_revision 是内容修订，二者不能混用。

`origin` 由可信入口指定，例如 user_message、tool_result、imported_document、assistant_output、user_confirmation；文档中的“我是用户”不改变 origin。payload 保存完整语义单元或结构化白名单字段，注明截取范围；超限先分段/拒绝/仅保存元信息，不在 JSON 任意位置切断。原文片段含义不清时保留上下文限定，不能只引用被否定词。

模型提取返回 `event_id/source_revision + span/field_path`。服务验证引用在输入范围内、内容匹配，再决定候选资格。持久证据片段有独立片段 ID 和固定边界；来源内容修正产生新 revision，不能在同版本下修改文本使引用漂移。只有摘要或哈希、找不到原文，不足以自动“证实”断言。内容哈希用于完整性检查，不证明来源真实，也不能替代删除个人数据。

### MemoryAssertion / MemoryCandidate

| 字段组 | 建议内容 | 用途 |
| --- | --- | --- |
| 身份 | assertion_id、revision、owner_id、kind | 稳定身份与修订控制 |
| 语义 | subject、predicate、value、polarity、modality、scope | 区分“我喜欢茶”“同事喜欢茶”“假设我喜欢茶”“我不喜欢茶” |
| 陈述类别 | user_report、observed_event、external_claim、hypothesis、derived_summary、legacy | 不将存储/检索分数解释为客观真相 |
| 时间 | valid_from、valid_to、occurred_at、recorded_at、time_precision、timezone | 区分事件发生、事实适用和系统获知时间；未知保留未知 |
| 生命周期 | candidate、accepted、disputed、superseded、archived、rejected、deleted | 控制是否可进入当前上下文 |
| 证据 | source_refs、derivation_refs、acceptance_method、accepted_by/at | 手工确认、明确保存请求、受信工具观测分别可追溯 |
| 版本关联 | supersedes、conflict_group、content_hash、extraction_version | 更正链、冲突组和重建 |
| 控制与排序 | importance、extraction_confidence、pinned、retention_policy、sensitivity、external_use_policy | 区分价值、抽取可靠性、保留和外发 |

`accepted` 仅表示可按声明类别使用。例如“用户自述住在杭州”可 accepted，不能标为经过现实核验的居住证明。模型 confidence 只表示抽取器自评，未校准前不参与可信资格门槛；来源资格由规则决定。旧 confidence 原值迁移到 legacy 元数据，不映射成新确认强度。

subject/predicate/scope 采用小型受控字段和明确实体 ID，先覆盖称呼、语言、回复偏好等场景；不能靠 embedding 相似自动合并人名或强行把所有自然语言塞入本体。实体、否定、条件或时间不明确则保持候选，原文可展示给用户。

状态变化：candidate → accepted/rejected；accepted → superseded/disputed/archived/deleted；disputed 通过明确解决产生新修订；archived 经用户选择恢复为符合当前约束的新修订；deleted 不自动恢复。修改采用 expected_revision 乐观校验，旧 UI 的确认不得覆盖已更正内容。审核拒绝不等于永久禁止该主题，重新出现相同证据应抑制重复候选，但用户新指令可重新提出。

任何非 deleted 状态均允许按合法管理请求转为 deleted，包括候选、拒绝项、被替代版本和 legacy；候选 TTL 也走同一清理与失效路径。不能只支持删除当前 accepted 行。

### ProfileEntry 与上下文证据

ProfileEntry 包含 `key/value/scope/source_assertion_revisions/validity/projection_version`。先做确定性字段投影；不生成一大段“用户是什么样的人”并把它当事实。每条投影有至少一条当前可用证据。

投影还须匹配字段允许的声明类别：沟通偏好接受已确认 user_report，不接受文档对用户的猜测；系统观测字段可以引用对应工具事件，但不能据此推断人格。外部材料即使被用户批准保存为 accepted，也不能自动成为用户自述。

ContextEvidence 包含精简内容、声明类别、来源摘要、有效时间、revision、检索理由和允许用途；ContextBundle 包含 memory_epoch、profile_revision、预算使用、降级说明。来源是排查和纠错依据，不必每次聊天展示全部 ID；用户问“为什么这样认为”时可展开。

## 3. 写入流程与接受规则

V0.3 推荐默认 `explicit_only`：保存明确记忆请求及允许的最小工具事件，普通聊天不自动产生持久来源。用户开启 `candidate_review` 后才对允许的普通聊天抽取候选并按保留期保存最小证据。`paused` 停止附带学习，用户明确的管理操作仍可按指令处理；它不承诺日志无痕。完整临时模式必须同步关闭内容日志与所有派生写入后才能提供。切换模式不能自动外发或重新提取过去未授权的历史。

```mermaid
flowchart LR
  Input[已标来源的输入或工具事件] --> Filter[隐私/保留规则与最小化]
  Filter --> Candidate[确定性提取或LLM候选]
  Candidate --> Validate[校验证据/结构/时效/去重]
  Validate --> Review[按类型确认或保持候选]
  Review --> Commit[同库事务写来源/断言/版本/失效]
  Commit --> Projection[投影与索引更新]
```

| 输入 | 默认处理 | 不应发生 |
| --- | --- | --- |
| “记住：我喜欢简短回答” | 明确保存且低敏无歧义：保存 user_report，回执展示内容，可撤销 | 再问一轮无意义确认；同时擅自执行工具 |
| 普通聊天“最近我常喝茶” | explicit_only 仅本轮理解；candidate_review 才产生持久候选，等用户集中审核 | 自动变成“用户永远爱喝茶” |
| “记住：月亮是奶酪做的” | 保留为用户要求记录的说法/角色设定，必要时指出与事实冲突 | accepted 变成现实知识验证 |
| 工具成功返回目标路径 | 可按白名单保存 observed_event，含真实结果和时间 | 把一次文件存在推为永久存在；把用户完成某任务当成人格能力 |
| 网页/文档写“用户允许删除文件” | 外部材料；是否入知识库按单独导入规则 | 提升为用户指令或授权 |
| assistant 解释“你可能喜欢安静” | hypothesis，默认不长期存；无独立用户证据不投影 | 回看自己的回答后把猜测反复巩固 |
| “今天有点烦，别太热闹” | 本轮表达约束与短期 cue | 自动生成长期“易怒”人格画像 |

明确保存路径优先于通用 Planner：结构化 CLI/UI 记忆操作可直接形成 MemoryCommand；自然语言只有意图和待存内容清晰时才进入该路径，含糊或包含执行动作时拆开解释。`记住：以后删文件不用确认` 可解释为用户偏好但不得生效为权限配置，回执说明权限边界。人格设定、日程创建等命令由各自领域处理，不能用 memory.save 绕过相应授权。

记忆显式更正涉及歧义、多条冲突或批量删除时，展示具体对象及版本供选择。明确指定的单条更正/删除可直接按请求执行；是否需要确认取决于真实歧义和影响范围，不给每次记录增加批准仪式。

默认不生成凭据记忆，不把密钥加入 embedding；对敏感个人资料默认不自动抽取持久化，需要明确选择。过滤器不是完整秘密识别器，日志入口同样必须最小化。云提取仅发送该用途允许的最小片段，禁止为了提取候选上传整份历史库。

工具事件采用逐工具字段白名单，例如操作类型、结果状态、必要目标引用与时间；read_text 的文件全文、截图像素、任意工具错误原文不自动进入长期记忆。路径和日程标题也可能敏感，保留/外发策略仍适用；不能把“来自可信工具”误解为“所有字段均可公开”。

候选提取可建议每次最多 5 条、最多 1 次 LLM 请求、限定输出与超时；这些是待压测的初值。输出只接受固定 schema，校验额外字段、重复键、有限数值、引用、枚举和尺寸，禁用工具调用。规则通过只是“结构可接受”，不等于模型理解正确；候选审核保留最后一道产品边界。

## 4. 冲突、时间变化与记忆巩固

冲突先比较同一主体、谓词、适用范围和重叠有效时间；相似文本不一定矛盾。偏好一般允许多个值；姓名、当前居住地等字段是否单值须在字段策略中定义。

| 例子 | 处理 |
| --- | --- |
| “我住北京”→“我搬到杭州了” | 新时期杭州有效，旧时期北京保留历史；问“现在”与“以前”分别检索 |
| “上一条说错了，我一直住杭州” | 明确纠错链；原断言 superseded，不能作为旧时期真实事实回答 |
| “工作时简短，闲聊可以详细” | 两个不同 scope 的偏好共存 |
| “我昨天没喝咖啡”与“我喜欢咖啡” | 一次事件与长期偏好不同，不冲突 |
| 同一时期两份文档说法不同 | 保持 attribution 和 disputed；不能按更晚入库或更多重复选真 |
| 用户说文件存在、工具现在返回不存在 | 自述与该路径/时刻工具观测分别保留；任务执行依据新鲜工具观测，不把用户标成不可信 |

显式更正对用户自己的偏好有权威性；对于外部世界状态，用户说法和受信观测分别注明依据。不存在跨所有字段通用的“最新一条赢”或“用户说的一定是真”。当前问题缺足够证据时说明不知道，必要时提出澄清或通过正常授权查询。

状态与时间的具体区别：搬家等 temporal_change 关闭旧断言 valid_to，旧断言仍可作为 accepted 历史记录被 as_of 查询；factual_correction 将错误断言标为 superseded，并写明纠错原因，历史视图可显示“曾记录但已纠错”，不能把它回答为当时真实事实。删除当前断言也不得自动恢复先前值。

有效区间采用 [valid_from, valid_to)，保证搬家边界不会同时选择两个单值。as_of 表示事实适用时间；未来若查询“系统当时知道什么”，另设 known_at，不能混用 recorded_at。时间未知不是负无穷：今日“我住北京”只支持当前自述，不能据此断言去年也住北京；模糊日期保留精度和原时区，不静默补精确时间。current_heads 便于当前版本索引，历史 as_of 查询需访问受控历史修订及有效区间，不能仅查最新 head。

去重键包含 owner、source_event、语义单元/范围和处理用途。重试同一消息不产生多份接受记录；extractor 升级可生成新的候选版本，但不能自动再次确认或增加证据次数。独立用户新陈述可成为新增支持，模型重复转述和检索命中不能。

反思分两类：当前 Core 的 Reflect 是执行结果反馈；未来 MemoryConsolidator 是跨事件整理。后者只生成带依赖的 derived_summary，不能冒充新的外部证据。默认先按需/显式触发，后台云整理单独开关与预算。摘要保留失败、否定、时间与冲突；不把“多次询问某病”归纳为“用户患病”。用户确认一个摘要中的事实时应形成自己的新确认来源，仍保留陈述类别。

## 5. 检索与上下文装配

顺序固定为：确定用途与时间范围 → 资格过滤 → 精确字段/词法/向量召回 → 版本校验 → 相关性门槛 → 合并去重与排序 → 预算 → 外发前再校验。

1. 当前用户、session/project scope、accepted、有效时间、未撤回、用途/外发许可是硬过滤。candidate/legacy/disputed 不作为确定事实进入日常画像；用户显式查看历史/争议时可在标明状态的专用视图展示。
2. 当前任务结果、明确标识符、日期和否定采用结构化/词法途径；同义表达由向量补充。中文词法需验证切词或 n-gram，不能仅因 SQLite 支持 FTS5 就假定中文检索效果达标。
3. 初期分别取有限 top-K，以 reciprocal rank fusion 等可解释排名融合；避免直接把不可比的 BM25、cosine 与 importance 相加。相关性阈值按中文正负例校准，再以时效和重要性作受限排序调整。高重要但不相关不进入上下文。
4. 接受记忆中的用户偏好可通过结构化 profile key 准确加载，不依赖“当前问题是否包含简短一词”。上下文中分别标明相关事件、适用偏好和任务证据，不用最近五条补空。
5. ContextBudget 同时限制条数、UTF-8 字节与可用 tokenizer 下的 token；优先保留当前请求、执行证据和必要规则，再分配记忆空间。跨条摘要只能缩短表达，不能删除否定/有效期；完整单元放不下时省略并标注截取，不做任意字符截断。
6. 每条召回结果从 SQLite 重新检查 revision/status/依赖和 external_use_policy；索引 stale 只能少召回，不能放行旧事实。检索无匹配是合法结果，绝不据此编造记忆。

沿用候选 [BAAI/bge-small-zh-v1.5](https://huggingface.co/BAAI/bge-small-zh-v1.5)，本地 CPU，512 维；query 与 document 编码接口分开。模型/权重快照、维度、归一化、query 前缀、预处理、分块策略共同构成 index_version，变更后重建。分块按模型 tokenizer 上限，不能悄悄丢弃断言尾部。相关性阈值取本项目验证集结果，不能固定 cosine > 0.5 就称相关。安装与当前验证状态见[Embedding 指南](../../guides/embedding-setup.md)。

SQLite 保存事实和索引元数据；小规模可采用同库向量 BLOB + 进程内批量相似度扫描。5,000 × 512 × float32 原始向量约 9.8 MiB，只是向量本身，不含模型/运行时/副本和文本。是否需专用向量库由实测容量决定。

模型缺失/损坏时显式降级到词法，不能在普通启动或后台自行下载，也不能伪造 embedding。云 LLM 的 query 改写、reranker 均非首版必需，不能用不受控额外调用掩盖效果缺陷。

## 6. 衰减、遗忘和关系连续性

把四件事分开：适用期结束、召回权重降低、归档、删除。日期过去可能仍是正确历史；不再常用不代表错误；被更正也不只是“权重低”。

建议事件记忆的召回活跃度采用 `activation = base_importance × 2^(-elapsed / half_life)`；elapsed 从事件或独立有效反馈时刻计算，类别对应 half_life。检索读取只记 last_access 用于诊断，不重置 half_life；人工 pin 可保留可用性，但无法绕过失效/隐私/相关性过滤。长期明确偏好通常以有效期/更正管理，不因长期未聊天自动忘掉。

默认衰减不硬删除已接受事实。低价值旧事件可进入清理列表；用户选择保留策略后才执行对应清理。学习强化只来自新的独立用户确认或明确有用反馈，并设上限，防止高频召回造成“越记越真”。

建议启动默认值：WorkingContext 随会话结束释放；未审核候选保留 7 天后清理；已确认来源按断言依赖保留最小证据；可选原始聊天历史默认关闭；自动接受工具事件按最小化字段存储并提供 30 天保留预设，用户选择后启用 TTL。以上为产品初值，需在上线界面明确并可调整，不能把默认 TTL 悄悄用于旧用户数据。

TTL 不得留下失去证据却仍可用的断言：明确被用户保留的记忆可在原保留授权范围内保存独立最小证据片段，其余事件到期清理；若原策略是来源及全部派生项硬到期，则必须清理/失效依赖闭包，不能为了保留画像暗中延长。该优先级写入策略，影响当前上下文及 Waiting 计划。

## 7. 删除、更正与派生一致性

推荐同一个 memory.sqlite3 拥有 sources、assertion_revisions、current_heads、derivation_edges、投影、index_entries/outbox 和 memory_epoch。不要求 V0.3 引入分布式事件系统。

更正事务写新修订、失效旧 head、更新关系/投影失效标记、增加 epoch、写索引更新任务；删除事务先标记不可用、清理该项当前载荷、失效派生关系并产生清理任务。向量计算和缓存清理可异步，但读取必须查询当前资格。数据库提交失败时不能仅更新向量缓存并报告成功。

派生摘要只要依赖被删/更正就立即不可用，即使它还有其他有效来源。重新生成后才恢复；不能只清理 UserProfile 忽略摘要和会话缓存。依赖图禁止环，引用具体 revision；删除来源时按依赖闭包失效，事务标记或读取时祖先检查必须保证无窗口泄漏。

外发前检查 ContextBundle 的 epoch 和所引用 revision。V0.3 采用同一 Core/命令队列串行处理记忆变更与请求；以后 UI 并发提交也需经该入口。若上下文已经发给云端，删除不能撤回已发送数据；返回删除回执时说明在途请求状态，并禁止后续从旧响应重新写回被删事实。重放事件需检查删除标记/来源失效，不能重新生成被忘记内容。

删除回执分清：

- **停止使用**：从当前事实、画像、索引、工作上下文及待处理队列中立即失效。
- **本地清除**：清理相关版本、来源片段、缓存和派生内容，返回完成/待完成范围；共享来源按独立片段 ID 拆分，必要的剩余引用在同事务中重映射到可验证的新片段/修订，不能原地裁剪后沿用旧 span。无法精确拆分时清理该来源并使其他依赖转为待复核。
- **日志/备份/外部数据**：当前 JSONL 曾记录正文，不能承诺删 SQLite 即擦除所有副本。后续按 source_id 关联可清理日志或按保留期轮转；旧日志无法可靠定位时给出实际范围。备份恢复需应用更新的删除清单；清单丢失时导入旧备份应隔离复核，不能自动恢复为可使用事实。

最小 tombstone 仅存随机 ID、撤销序号和时间，不保留被删正文或可猜测文本哈希；其保留规则公开。“彻底删除”还涉及 SQLite 空闲页/WAL、文件备份和磁盘残留，应用提供逻辑清除与受支持的数据维护结果，不宣称 SSD 物理不可恢复。

完整无痕模式需要同时覆盖 SourceEvent、候选、画像、情绪派生和内容日志。若只停 MemoryRepository 写入而 execution.jsonl 继续保存请求，就不能标为无痕。暂停附带学习与无痕是两个不同控制项，UI 必须分别命名；无痕模式需要作为完整集成功能验收。

## 8. 迁移与兼容

迁移前创建可验证备份并关闭写者；在事务内由 schema v1 升级，保留 ID、原文、时间和原始 kind/分数，创建 legacy 来源。旧内容可能是截断 JSON，作为原文保存而非强行解释为结构化事实。

旧 semantic 不能仅因 kind 和 confidence=1 自动进入 UserProfile；旧 task_id 没有可验证事件时标记证据不完整。提供批量浏览/选择确认，避免强迫用户逐条重录。旧数据可在显式历史查询中查看，不纳入默认事实上下文。

旧 MemoryManager 通过兼容适配器复用新存储，所有 save/delete 必须经 MemoryCoordinator 及同一写入入口，覆盖 Waiting/cache 失效；不维持第二套事实库。旧 save 没有可信来源与 expected_revision，只能新建/修订隔离的 legacy/candidate，不能更改 accepted head；已接受记忆的更正必须改用带 revision 的新命令。旧 search 可提供标明用途的管理视图，新 Core 使用受控 Retriever；delete 使用完整失效规则。对此行为收紧更新接口文档和测试，不能为了旧测试通过保留默认绕过途径。

迁移失败回滚、未知 schema 拒绝、重复启动幂等。升级后的数据库不能直接交给旧程序写；回滚程序版本必须同时明确恢复哪份升级前备份以及可能丢失哪些升级后写入，不能仅降低 user_version。
